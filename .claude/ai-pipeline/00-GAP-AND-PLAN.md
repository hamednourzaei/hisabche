# Agentic Accounting Pipeline — وضعیت فعلی، شکاف‌ها و برنامه

> ۶ اکتبر ۲۰۲۶ · **منتظر تأیید صاحب پروژه — هیچ کدی برای این کار نوشته نشده.**
> خواسته: ارتقای AI از «بخوان و جواب بده» به پایپ‌لاین
> Understand → Investigate → Ask → Reason → Propose → Execute → Validate → Post → Verify → Audit
> پشت پرچم `ai_pipeline_v2`.

---

## ۱. آنچه الان هست (از روی کد، نه حدس)

دو مسیر AI **جدا** داریم که هیچ‌کدام کل پایپ‌لاین نیستند:

### الف) دستیار داخل برنامه — فقط خواندنی

|       |                                                                                                                                          |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| مسیر  | `POST /api/ai/ask` → `backend/src/services/ai/ai-chat.service.ts`                                                                        |
| جریان | سؤال → مدل از **۴ نمای بسته** انتخاب می‌کند → `ReportingReader` با **توکن خودِ کاربر** (RLS) می‌خواند → مدل جواب می‌دهد → `ai_query_log` |
| نماها | `inventory_summary`، `customer_balance`، `sales_summary`، `outstanding_invoices`                                                         |
| نوشتن | ندارد. هیچ ابزاری برای تغییر داده نیست.                                                                                                  |
| لاگ   | `ai_query_log` (سؤال، جواب، نماها، مدل، زمان). متن سند/عکس ذخیره نمی‌شود.                                                                |

### ب) دروازه‌ی MCP — برای دستیارهای بیرونی (با کلید API)

|         |                                                                                                                                                                        |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| مسیر    | `POST /mcp` → `backend/src/routes/mcp.routes.ts` + `services/mcp/mcp-tools.ts`                                                                                         |
| ابزارها | ۲۶ ابزار؛ هر ابزار = **یک route از Public API** (`API_ROUTE_SCOPES`). هیچ ابزار SQL یا منطق تجاری جدا ندارد.                                                           |
| اجرا    | با `fastify.inject` و همان اعتبارنامه → احراز، scope، اعتبارسنجی، idempotency و رویدادها همان کدِ مسیر دستی است.                                                       |
| تأیید   | ابزار `financial`/`destructive` اجرا نمی‌شود؛ ردیف `ai_action_requests` می‌شود و مدیر در برنامه تأیید/رد می‌کند. اجرا با نشست همان شخص و `Idempotency-Key = mcp-<id>`. |
| لاگ     | `ai_action_requests` (ابزار، آرگومان، تصمیم‌گیر، کد و بدنه‌ی نتیجه) — forward-only با trigger.                                                                         |

### ج) زیرساخت‌هایی که پایپ‌لاین باید از آن‌ها عبور کند (و موجودند)

- **مجوز:** `resolveEffectiveAccess` → `tenancy.capabilities`؛ `requireCapability` روی هر route. (۶ اکتبر: نقش سفارشی واقعاً اعمال می‌شود.)
- **Domain Engine:** `InvoiceService.create`، `payments`، `manufacturing_complete`، … — نوشتن چندجدولی با تابع Postgres (`.rpc()`).
- **Idempotency:** هدر `Idempotency-Key` → `client_request_id` / `sourceIdOf(...)` در فاکتور، پرداخت، کالا، مشتری، انتقال انبار.
- **Audit عمومی:** `logBusinessEvent` + `entity_notes`/`data_snapshots` (append-only با trigger).

## ۲. شکاف‌ها — مرحله به مرحله

| مرحله                | الان                                                                                            | شکاف                                                                                                                                                                     |
| -------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Understand**       | مدل فقط نما انتخاب می‌کند. intent ساختاریافته نداریم.                                           | نیاز به schema بسته‌ی intent (نوع عملیات، entity، پارامترها) + فیلد صریح `uncertain[]`.                                                                                  |
| **Investigate**      | ۴ نمای تجمیعی، با RLS کاربر.                                                                    | برای یک عملیات کافی نیست: موجودی یک کالا، مانده‌ی یک مشتری، نسخه‌ی فعلی یک فاکتور خوانده نمی‌شود. خواندن باید از **همان routeهای موجود** باشد (مثل MCP)، نه reader تازه. |
| **Ask missing info** | ندارد. مدل یا جواب می‌دهد یا می‌گوید «نمی‌دانم».                                                | حالت `needs_input` با سؤال‌های نام‌دار؛ تا پاسخ نیامده هیچ write.                                                                                                        |
| **Reason**           | استدلال فقط در متن جواب است و ذخیره نمی‌شود.                                                    | ذخیره‌ی `reasoning_snapshot` ساختاریافته (قاعده‌های اعمال‌شده، داده‌ی مبنا).                                                                                             |
| **Propose**          | در MCP: «آرگومان ابزار». diff انسانی نداریم.                                                    | ساختار `entity / field / from / to / reason` + نمایش در UI.                                                                                                              |
| **Confirm**          | در MCP هست (`ai_action_requests`)، ولی فقط برای کلید API. دستیار داخلی اصلاً نوشتن ندارد.       | یکی‌کردن: دستیار داخلی هم همان صف تأیید را بسازد. auto-approve با آستانه **وجود ندارد**.                                                                                 |
| **Execute**          | در MCP درست است (inject به route).                                                              | استفاده‌ی همان `runRoute` برای پایپ‌لاین داخلی — مسیر write دوم ساخته نشود.                                                                                              |
| **Validate**         | اعتبارسنجی داخل خودِ route/سرویس (zod + قاعده‌ی دامنه + تابع DB). مرحله‌ی جدا و گزارش‌شده نیست. | «پیش‌اعتبارسنجی» قبل از تأیید: فقط چیزهایی که بدون نوشتن قابل‌سنجش‌اند (schema، موجودی، سقف اعتبار، مجوز). بقیه در خودِ تراکنش می‌ماند.                                  |
| **Post**             | همان تراکنش route.                                                                              | چیزی لازم نیست — نباید مسیر جدا ساخته شود.                                                                                                                               |
| **Verify**           | ندارد: نتیجه = کد HTTP پاسخ.                                                                    | خواندن دوباره‌ی entity بعد از commit و مقایسه با diff پیشنهادی.                                                                                                          |
| **Audit**            | دو لاگ جدا (`ai_query_log`، `ai_action_requests`)، هیچ‌کدام کل زنجیره را ندارد.                 | یک جدول append-only: یک ردیف به‌ازای هر **مرحله** از هر run، قابل بازیابی از روی فاکتور/سند.                                                                             |
| **dry-run**          | ندارد.                                                                                          | run ای که تا Propose می‌رود و هرگز Execute نمی‌شود.                                                                                                                      |
| **feature flag**     | در بک‌اند زیرساخت پرچم عمومی **ندیدم** (UNKNOWN: شاید جای دیگری باشد).                          | یک تنظیم workspace با پیش‌فرض خاموش.                                                                                                                                     |

### سه نکته که با متن خواسته فرق دارد و باید بدانی

1. **«mutation_id در packages/sync»** — مسیر idempotent بک‌اند با هدر `Idempotency-Key` کار می‌کند، نه با نامی به‌اسم `mutation_id`. پایپ‌لاین از همان هدر استفاده می‌کند (مثل MCP: `mcp-<id>`). کلید قطعی از شناسه‌ی run ساخته می‌شود.
2. **«version-based optimistic concurrency»** — برای فاکتور و پرداخت، قفل نسخه‌ای عمومی **ندیدم** (UNKNOWN، باید قبل از ادعا بررسی شود). Verify این را پوشش می‌دهد: اگر entity بین Propose و Execute عوض شده باشد، اجرا رد می‌شود.
3. **اعتبارسنجی «قبل از commit»** برای قاعده‌هایی که فقط دیتابیس می‌تواند بسنجد (موجودی هم‌زمان، یکتایی) باید **داخل همان تراکنش** بماند. پیش‌اعتبارسنجی فقط هشدار زودهنگام است، نه جایگزین.

## ۳. اصل طراحی

**پایپ‌لاین یک هماهنگ‌کننده است، نه موتور دوم.** هر چیزی که می‌خواند یا می‌نویسد از routeهای موجود رد می‌شود (همان `runRoute` دروازه‌ی MCP با نشست خودِ کاربر + `x-workspace-id`). پس مجوز، scope، idempotency، اعتبارسنجی و رویدادها **همان کد مسیر دستی** است و چیزی کپی نمی‌شود.

```
ai_pipeline_runs (یک ردیف برای هر درخواست)
   └── ai_pipeline_steps (append-only: understand, investigate, ask, reason,
                          propose, confirm, execute, validate, verify)
```

مدل فقط در سه مرحله صدا زده می‌شود (Understand، Reason/Propose، و جمله‌بندی پاسخ)؛ بقیه کد قطعی است.

## ۵. تصمیم‌هایی که با توست

1. **دامنه‌ی اول:** پیشنهاد من سه عملیات است — ساخت فاکتور، ثبت پرداخت، ساخت/ویرایش مشتری. حذف، برگشت سند و بستن دوره در دور اول **نباشد**.
2. **auto-approve:** پیشنهاد من: ساخته شود ولی خاموش، و حتی روشن هم فقط برای عملیات غیرمالی. برای مالی همیشه تأیید آدم.
3. **چه کسی تأیید می‌کند:** خودِ کاربری که خواسته (اگر مجوز همان عملیات را دارد)، یا مثل MCP فقط مدیر/مالک؟
4. **هزینه:** هر run حداقل سه بار مدل را صدا می‌زند (الان دو بار). سهمیه‌ی ماهانه باید run را بشمارد یا call را؟

## ۶. ریسک‌هایی که می‌ماند

- مدل می‌تواند intent را غلط بفهمد؛ دفاع = diff + تأیید آدم + Verify، نه اعتماد به مدل.
- متنِ داخل داده (نام مشتری، یادداشت) می‌تواند دستور جعلی باشد؛ مدل هرگز route یا SQL انتخاب نمی‌کند، فقط از فهرست بسته.
- بین Propose و Execute داده می‌تواند عوض شود؛ Verify و قاعده‌های تراکنشی آن را می‌گیرند، ولی کاربر یک «رد شد، دوباره بررسی کن» می‌بیند.
