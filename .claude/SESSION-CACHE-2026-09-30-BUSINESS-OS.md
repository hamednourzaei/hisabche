سه قابلیت از ۱۵۰گانه که در استخراج اول «موجود» به نظر می‌رسیدند، یکی‌شان نبود:

| ---------------- | ---------------------------------------------------------------------------- |

| #۷۰ Depreciation | کامل، فقط **بدون زمان‌بندی**. فقط یک worker لازم بود                         |

**قاعده:** فرضِ «این هست» را با `grep -rn` روی کلاینت بسنج، نه با وجود فایل.
یک backend کامل با صفر UI consumer، از نیمه‌ساخته بودن بدتر است.

## ۲. ⚠️ `zod-to-json-schema` با `exactOptionalPropertyTypes` نمی‌کند

`TS2589 — Type instantiation is excessively deep` و بعد ۱٫۵ گیگ استک.

هر schema دارای `ZodOptional` در این monorepo، به یک `ZodEffects` می‌رسد که TS
بازش نمی‌کند. راه‌حل:

- body را با `z.any()` بگذار و **در handler** با `schema.parse(request.body)` اعتبارسنجی کن
- بلوک `schema` برای routing و مستندات Fastify است، نه برای validation

⚠️ و در `accounting.routes.ts` یک helper محلی `toJsonSchema` وجود دارد که خودش
`zodToJsonSchema` را صدا می‌زند — **همان محدودیت را دارد**. import مستقیم از
کتابخانه مشکلی نیست، `.extend()` و `z.optional()` است.

## ۴. ⚠️ تستی که تاریخ نمی‌سازد، تاریخ غیرممکن می‌سازد

```ts
receivedDate: `2026-09-${1 + days}` // days=30  →  "2026-09-31"
```

JavaScript `2026-09-31` را **بی‌صدا** به ۱ اکتبر تبدیل می‌کند. تست قرمز نمی‌شود
با «تاریخ نامعتبر» — چیز دیگری را اندازه می‌گیرد.

```ts
// ✅ درست
new Date(Date.UTC(2026, 8, 1 + days)).toISOString().slice(0, 10)
```

همین الگو در `addMonths` هم بود: **تاریخ یک مدت نیست**، و `Date` + یک ماه
روی ۳۱، دو ماه بعد را رد می‌کند.

## ۵. ⚠️ «پیش‌فرض خاموش» با مقایسه‌ی عدد بیان نمی‌شود

```ts
// ❌ با minScore: 0 ، شرط هرگز برقرار نمی‌شود → «خاموش» در واقع «روشن» است
if (suggestion.score < settings.minScore) {
  refuse()
}
// ❌ تلاش دوم، همان مشکل
if (suggestion.score <= settings.minScore) {
  refuse()
}

// ✅ باید صریح باشد
if (settings.minScore <= 0) {
  refuse()
}
```

دو تلاش ناموفق لازم بود. قاعده: **وقتی یک مقدار، حالت «غیرفعال» را هم
بیان می‌کند، آن حالت یک شرط جداگانه است، نه یک عدد که با مقایسه ساخته می‌شود.**

هم‌خانواده: `<` در برابر `<=` در آستانه‌ی تمرکز. **دقیقاً روی آستانه یعنی
ریسک**، نه «زیر آستانه و پس سالم».

## ۶. ⚠️ گاردی که خودش را می‌گیرد

نوشتن `ROUNDING_DECLARATION` به‌صورت literal باعث شد **خودِ فایل گارد** تنها
فایلی باشد که `round2` را تعریف می‌کند. راه‌حل: ساخت regex با الحاق:

```ts
const ROUNDING_DECLARATION = new RegExp(
  ['function' + '\\s+round2\\b', 'function' + '\\s+roundMoney\\b'].join('|'),
)
```

⚠️ همان خانواده‌ی BUG-029 (کامنتی که رگکس را تغذیه می‌کند).

**و نسخه‌ی اول guard من ۴۰+ false-positive داد** — از جمله
`AccountingService.postDocument`، پرکاربردترین متد سیستم، که فقط از routes
فراخوانی می‌شد نه از serviceهای دیگر. **guardی که ۴۰ بار الکی قرمز می‌شود،
حذف می‌شود و حذف‌شده هیچ‌چیز را محافظت نمی‌کند.**

## ۷. ⚠️ مقیاس و مرز باید با هم بخوانند، نه جدا از هم

دو موتور که در این سشن نوشته شدند، هر دو با همین مشکل خوردند:

**مورد supplier risk:** وزن = `(days / 14) × 100` می‌شد ۳۶ برای ۵ روز تأخیر —
زیر آستانه‌ی ۴۵ «moderate»، پس تأمین‌کننده‌ای که **همیشه یک هفته دیر می‌رسید**
«ریسک پایین» گزارش می‌شد. اصلاح: `(days / 10) × 100`.

**مورد working capital:** انتظار تست از محاسبه‌ی دستی خودم آمده بود و غلط بود —
موتور درست بود، تست غلط.

> **قاعده:** هر دو ثابتِ یک مقیاس را کنار هم بنویس. اگر `weight` و
> `bandThreshold` در دو جای فایل باشند، هیچ‌کدام نمی‌فهمد دیگری چه می‌گوید.

## ۹. ⚠️ گردکردن با تقسیم جابه‌جا نمی‌شود

```ts
expect(quarterly).toBe(Math.round(monthly / 3)) // ❌
// 33,242,009 ≠ 299,178,082
```

هر دو یک نسبت درست‌اند ولی یکی روی مقدار **گردشده** حساب می‌شود. تست باید
یا روی **مقدار اصلی** مقایسه کند یا نسبت را با تلورانس بسنجد — نه انتظار
محاسبه‌ی دستی که خودم از ذهن درآورده بودم.

## ۱۰. ⚠️ «همان اسم، واحد متفاوت» — و هرکدام درست

`sumMinorUnits` **دو** نسخه داشت و هر دو درست بودند:

- `accounting.domain` → **minor** (عدد صحیح)؛ دفتر با minor کار می‌کند
- `utils/money.sumRounded` → **major**؛ نمایش با major

یکی‌شان‌کردنشان ترازنامه را ۱۰۰ برابر می‌کرد. **به‌جای یکی‌کردن، اسم دوم
جدا شد** (`sumRounded`) و یک تست تفاوت واحد را assert می‌کند.

> **قاعده:** دو تابع هم‌نام با واحد متفاوت، دلیلِ زنده‌ماندنِ چهار کپی
> `round2` بودند. اسمِ گمراه‌کننده را عوض کن، نه رفتار را.

## ۱۱. ⚠️ Fixture با واحد اشتباه، تست را به تستِ غلط تبدیل می‌کند

`OpenInvoice.total` **major** است (از `invoices.total` مستقیم). من با
`total: 100_000` فکر می‌کردم minor است — یعنی ۱۰۰٬۰۰۰٬۰۰۰. نتیجه: هر دو
تست «زیر حداقل» و «.bad debt» به‌جای رد شدن، `remind` برگرداندند.

> قبل از نوشتن fixture، **یک مقدار واقعی از سرویس یا اسکیما بخوان** و همان را
> بگذار. عدد ساختگی در یک fixture، یک تست است که چیز دیگری را می‌سنجد.

## ۱۲. ⚠️ «سه مکانیزم job» در استخراج اول، پنج تایمر و دو مالک بود

استخراج م基于 فقط `setInterval` را دیده بود و گفته بود «۳ مکانیزم». کد:
**۵ تایمر**، که فقط **۲** تایشان مالک کار قابل‌claim بودند و هر دو مرده
(صفر caller). بقیه **مصرف‌کننده** بودند نه رقیب:

| فایل                       | نقش                                          |
| -------------------------- | -------------------------------------------- |
| `job-scheduler.plugin.ts`  | poller که **claim می‌کند**                   |
| `scheduler/index.ts`       | cron که هر tick را `runScheduledOnce` می‌کند |
| `instance-registry.ts`     | heartbeat صفحه‌ی admin                       |
| `sync-stream.ts`           | یک poller به‌ازای هر workspace، فقط می‌خواند |
| `sync-stream.routes.ts`    | heartbeat هر WebSocket                       |
| `system-metrics.routes.ts` | sampling متریک                               |

⚠️ **ممنوع کردن timer اشتباه بود** — هر پنج را قرمز می‌کرد. چیزی که باید ممنوع
شود **صفِ خودش** است، نه ساعتی که claim می‌کند.

## ۱۳. ⚠️ whitelist بسته‌ی نام، یک cron امن را غیرقانونی می‌کند

```ts
// ❌Distributed-work.test.ts قبلی
const guarded = src.match(/await run(TrialExpiration|EventRecovery)Tick\(\)/g) ?? []
```

افزودن cron سوم (استهلاک) تست را قرمز کرد: «۲ تا داشت، ۳ انتظار داشت».
راه درست، تطبیق **شکل** است نه فهرست اسامی:

```ts
const guarded = src.match(/await run\w+Tick\(\)/g) ?? []
```

> **قاعده:** هر guard که **فهرست بسته** دارد، باید به‌ازای هر عضو جدید ویرایش
> شود — و آن لحظه‌ای است که کسی به‌جای «قاعده را درست کن» «تست را شل کن».

## ۱۴. ⚠️ یک گارد ساختاری، کار را پیش از بازبینی متوقف کرد

چهار guard موجود کار فاز ۱ را گرفتند و **همه چهار یک ایراد واقعی بودند**:

| guard                    | ایراد من                                |
| ------------------------ | --------------------------------------- |
| `no-silent-row-cap`      | `.limit(10_000)` — سقف PostgREST بی‌صدا |
| `distributed-work`       | whitelist بسته (بند ۱۳)                 |
| `concurrency-safety-map` | route جدید ثبت نشده بود                 |
| `unwired-capability`     | symbol حالا caller داشت                 |

⚠️ **این دقیقاً همان چیزی است که guard برایش ساخته شده.** بدون آن‌ها چهار
مشکل بی‌سروصدا به بعد می‌رسیدند.

## ۱۵. ⚠️ یک ثبت (register) باید دوطرفه باشد

وقتی `monthEndsFiscalYear` wire شد، guard گفت «caller دارد، status را عوض کن».
خوب. ولی اگر تست فقط `WRITTEN_NOT_WIRED` را assert می‌کرد، می‌شد **هر symbol
را به `WIRED` برد** و ساکت ماند — و قابلیتی که caller خود را از دست داده بود
«تمام‌شده» ثبت می‌شد.

هر دو طرف تست شد:

- `WRITTEN_NOT_WIRED` ⟹ صفر caller
- `WIRED` ⟹ **دست‌کم یک** caller

## ۱۶. ⚠️ «قابلیت هست» یعنی کسی صدایش می‌زند

سه مورد در این سشن پیدا شد که **درست، تست‌شده و بی‌مصرف** بودند:

| نمونه                               | وضعیت                                                     |
| ----------------------------------- | --------------------------------------------------------- |
| `shouldEscalate` / `escalatedRole`  | قابلیت #۶۸ · صفر caller · نه در validation · نه در اسکیما |
| `planRepost` / `allocateLandedCost` | گام سوم #۶۹ · صفر caller                                  |
| `queue.ts` · `queue/pdf-queue.ts`   | صفر caller · بدون persist · BullMQ جدا با Redis خودش      |

⚠️ **`src/queue.ts` یک in-process array بود با سه تابع بدون caller.** درست و
بی‌استفاده — و حلقه‌ی import آن یک چرخه‌ی ماژول بالقوه بود.

**تصمیم مالک:** نگه‌داشتن با وضعیت صریح، نه حذف (§۱۴ حذف برای کدی است که
اشتباه فهمیده شده). گارد `unwired-capability.test.ts` دفترِ صریح نگه می‌دارد و
**برای سبزشدن باید ردیف حذف شود**.

## ۱۷. ⚠️ زمان‌بندی روزانه برای استهلاک، ماهانه نه

ماهانه یعنی «ماهی که اجرا نشد، ماهی است که استهلاکش اتفاق نیفتاد» (درس ۳۴).
ولی `postDue` هر ردیف را با **تاریخ خودش** ثبت می‌کند، پس اجرای دیرهنگام هم
درست است. روزانه:

- یک خواندن index‌شده از ردیف‌های `posted_at IS NULL` که معمولاً **صفر** است
- و یک اجرای دیرهنگام، ده ردیف را با ده تاریخ حسابداری درست ثبت می‌کند

---

## ۱۸. ⚠️ نقش `owner` برای اجرای زمان‌بندی‌شده — صریح، نه پنهان

`CurrencyService.revalue` و `setPeriodLock` هر دو نقش owner/manager می‌خواهند.
کار زمان‌بندی‌شده کاربر ندارد. `monthEndContext` و worker استهلاک نقش `owner`
می‌گیرند و **در هر دو فایل کامنت شده**:

> این یک تصمیم مجوزدهی واقعی است، نه فنی. موتور هیچ تصمیم مجوزی نمی‌گیرد —
> فقط حساب‌ها و مبالغ را حل می‌کند. اگر بعداً guard اضافه شود که این نقش را
> بخواند، **همان‌جا** باید تصمیم بگیریم اجرای زمان‌بندی‌شده چطور مجاز است.

---

## ۱۹. ⚠️ «بنفرض نیست، پس امن است» — درباره‌ی قیمت‌گذاری هم صادق است

`pricing.domain` می‌پرسد قیمت کف هست یا نه. اگر **غایب** باشد یعنی «کفی
نیست» — نه صفر. اگر کف را از `buy_price` می‌ساختیم، هر تخفیفی در محصول بی‌صدا
کلمپ می‌شد و هیچ‌کس نمی‌توانست بگوید چرا.

هم‌شکل: `unavailable` ≠ `failed` ≠ `nothing_to_do`. سه حالت متفاوت‌اند و
هرکدام کار دیگری برای آدم می‌سازند.

---

## ۲۰. ⚠️ تاریخ شمسی/میلادی در test fixture هم می‌تواند گمراه کند

`2026-09-01` در همه‌جا **میلادی** است. `toIsoDay` همیشه میلادی برمی‌گرداند.
در `addMonths` از `Date.UTC` استفاده شد نه `new Date(string)` — چون رشته‌ی
تاریخ بدون timezone در برخی محیط‌ها UTC تفسیر می‌شود و در برخی محلی، و
نتیجه **یک روز** اختلاف دارد.
