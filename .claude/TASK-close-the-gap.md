# تسک: بستن شکاف با رقبا

## قانون بنیادی

بلوغ رقبا را **قرض بگیر**، محصولشان را کپی نکن.

مستندات عمومی Odoo · ERPNext/Frappe · NetSuite · SAP B1 · Dynamics 365 BC
حاصل بیست سال برخورد با حالت‌های لبه‌ای است. آن‌ها **جمع‌آوری نیازمندی رایگان**
هستند — بخوان تا بفهمی چه چیزی را فراموش کرده‌ای، نه تا شبیهشان شوی.

بگیر: **رفتار · حالت لبه‌ای · معماری اطلاعات · قواعد اعتبارسنجی**
نگیر: **رنگ · فونت · فاصله · کامپوننت · صفحه‌بندی · برندینگ**

منبع بصری همیشه `packages/ui` است.

---

## تشخیص پایه

بک‌اند و مدل دامنه از UX جلوترند. مشکل «معماری ضعیف» نیست؛ مشکل این است که
**قرارداد ساخته شده و مصرف‌کننده ندارد**. بزرگ‌ترین ریسک از این نقطه، اضافه‌کردن
فیچر جدید نیست — **شکستن یکدستی هنگام رشد** است.

⚠️ هر فیچری که خارج از قراردادهای `packages/ui-contract` ساخته شود، کیفیت کل
معماری را پایین می‌آورد. این قانون بر همه‌ی موارد زیر مقدم است.

---

## قوانین غیرقابل‌مذاکره

1. **بدون تکرار.** قبل از ساخت، `.claude/architecture/api-surface.md` و
   `packages/ui-contract/src/consolidation.ts` را بخوان. اگر چیزی از قبل آن سؤال
   را جواب می‌دهد، **گسترشش بده**. حقیقتِ رویدادِ پنجم، موتور مالی دوم، و دو
   مسیر به یک مقصد همه تست دارند و قرمز می‌شوند.
2. `workspace_id` تنها مرز است. `user_id` هرگز فیلتر نیست.
3. پول = واحد صحیح. نوشتن چندجدولی = تابع Postgres با `.rpc()`.
4. هفت لایه یا هیچ: `domain → service → routes → migration → hooks → container → page`
5. بدون رشته‌ی سخت‌کدشده. `fa / af / en` هر سه.
6. **کم‌نمایی بهتر از دروغ.** شمارشی که خوانده نشد `null` است نه صفر.
7. **تست سبز اثبات نیست.** برای هر مورد مهم: unit + integration + HTTP واقعی +
   **یک بار دیدن در مرورگر**.

## P0 — قبل از هر فیچر جدید

### P0.1 · شکاف قرارداد API را صفر کن

`KNOWN_MISSING` در `client-route-contract.test.ts` هفت endpoint دارد که کلاینت
صدا می‌زند و سرور ندارد — هر کدام امروز ۴۰۴ می‌دهد:

```
GET /v1/activities/entity/:type/:id            + /summary
GET /api/v1/entities/:type/:id/summary         + /activities
DELETE /employees/:id
GET /purchase-orders/:id
GET /transactions/ledger
```

کلاینت نباید endpoint خیالی داشته باشد. یا بساز، یا صدا زدنش را حذف کن.
**هر خطی که از `KNOWN_MISSING` کم می‌شود باید یک endpoint واقعی پشتش باشد.**

### P0.2 · هر قراردادی که مصرف‌کننده ندارد را وصل کن

`list-engine` · `entity-views` · `work-queue` · `work-state` ساخته و تست‌شده‌اند.
هر کدام باید **حداقل دو صفحه‌ی واقعی** مصرفش کند، نه یکی.

⚠️ درسی که گران تمام شد: `scope.domain.ts` یک سشن کامل درست و کاملاً تست‌شده بود
و **هیچ‌کس صدایش نمی‌زد** — فروشنده همچنان می‌توانست فاکتور دیگری را ویرایش کند.
قراردادِ بی‌مصرف‌کننده، فاز تمام‌شده نیست.

### P0.3 · یک E2E واقعی مرورگر

یک مسیر کامل «یک روز کاری» در مرورگر: ورود → فاکتور → پرداخت → دفتر → گزارش.
تا این نباشد، هیچ ادعای production-ready معتبر نیست.

## بخش A — چهار موردی که باید به ۱۰ برسند

### A1 · عمق مجوز (۷ → ۱۰)

مرجع: ERPNext _User Permissions_ · NetSuite _Role & Permission_ · SAP B1 _Authorizations_

- `scopes.assertMay()` را به **همه‌ی** endpointهای تغییردهنده وصل کن، نه دو تا.
  `scope-wiring-guard.test.ts` را طوری گسترش بده که هر `PATCH/PUT/DELETE` روی
  جدول مشترک را الزامی کند.
- ماسک سطح‌فیلد را از hardcode به **پیکربندی per-role** ببر.
- SoD را در **لحظه‌ی ثبت** اجرا کن، نه فقط در تنظیمات.
- endpoint «چرا نمی‌توانم؟» — دلیل رد به زبان کسب‌وکار.
- دسترسی **زمان‌دار** و **تفویض در غیاب**، با ثبت در `audit_logs`.

### A2 · دفتر و حسابرسی (۷ → ۱۰)

مرجع: ERPNext _Accounting_ · Odoo _Accounting_ · D365 BC _Finance_

- سه صورت مالی از `journal_lines`: **سود و زیان · ترازنامه · جریان وجه نقد**.
- **بستن سال مالی** + انتقال مانده‌ی افتتاحیه.
- **ریزبینی GL**: از یک عدد در گزارش تا سطر سند.
- گزارش بر اساس **ابعاد** (`accounting_dimensions` از قبل هست).
- **نمایشگر مسیر حسابرسی** که تغییرناپذیری `audit_logs` را نشان دهد.
- سند **اصلاحی/برگشتی** به‌عنوان جریان، نه `DELETE`.

### A3 · بهای تمام‌شده انبار (۷ → ۱۰)

مرجع: ERPNext _Stock Reconciliation & Valuation_ · Odoo _Inventory Valuation_

- **روش بهای تمام‌شده per گروه کالا**: FIFO (هست) + میانگین موزون + استاندارد.
- **شمارش انبار** با ثبت سند انحراف.
- **انتقال بین‌انباری با کالای در راه**.
- سیاست **موجودی منفی**: رد یا هشدار، per workspace.
- **نقطه‌ی سفارش** روی `min_stock_level` که از قبل هست.

### A4 · گردش‌کار و تأیید (۶ → ۱۰)

مرجع: ERPNext _Workflow_ · Odoo _Approvals_ · SAP B1 _Approval Procedures_

- **مسیریابی شرطی** بر اساس مبلغ/بعد/شعبه — از `business_rules` استفاده کن.
- **ماتریس تأیید بر اساس مبلغ**.
- تأییدکننده‌های **موازی** + **تفویض در غیاب**.
- **تشدید بعد از مهلت** (`node-cron` از قبل هست).
- **تأیید گروهی** + پاسخ به «چه کسی باید تأیید کند؟ بعدش چه می‌شود؟»

## بخش B — زیر ۵ که باید به ۷–۸ برسند

### B1 · نماهای عمومی (بزرگ‌ترین شکاف واقعی)

`entity-views.ts` قرارداد دارد، ولی Board/Calendar/Timeline/Analytics **رندر
نمی‌شوند**. این جایی است که بک‌اند ۹.۵ و UX ۷.۸ می‌شود.

```
ENTITY → List · Detail · Form · Board · Calendar · Timeline · Analytics
```

⚠️ هر نما یک کامپوننت **مشترک** در `packages/ui` است که همه‌ی موجودیت‌ها مصرف
می‌کنند. هیچ دامنه‌ای UI مخصوص خودش نمی‌سازد. وقتی نمایی ساخته شد، همان لحظه به
`ENTITY_VIEWS` اضافه شود — نه زودتر.

### B2 · گزارش‌گیری (۳ → ۸)

⚠️ **موتور کوئری جدید نساز.** `SavedView` در `list-engine.ts` و
`accounting.service` از قبل هستند.

- سازنده‌ی گزارش روی همان `ListQuery`: ستون · فیلتر · گروه‌بندی · جمع.
- ذخیره‌ی گزارش = همان `SavedView`، نه جدول جدید.
- خروجی از همان `/api/migrations/export`.
- داشبورد per role از `DOMAIN_SPECS`.

### B3 · یکپارچه‌سازی (۲ → ۸)

⚠️ `webhook.service.ts` و core `plugins` از قبل هستند — **گسترششان بده**.

- تحویل webhook با **امضا + تلاش مجدد + صف مرده**.
- **کلید API با scope** — از همان `CAPABILITIES`، مجموعه‌ی جدید نساز.
- **ورود صورت‌حساب بانکی** — `bank_statements` هست، فقط parser می‌خواهد.
- SDK افزونه با همان مرز `intelligence.ts`.

### B4 · موبایل (۵ → ۸) — با یک تغییر اصل

۱۸ مقصد از ۳۳ پیاده است. ولی **موبایل نباید دسکتاپ کوچک‌شده باشد**:

```
دسکتاپ → چگالِ اطلاعات   (جدول، تحلیل، چندستونی)
موبایل  → چگالِ عمل       (ثبت فروش، دریافت پول، جست‌وجوی کالا،
                            جست‌وجوی مشتری، کارهای امروز، وضعیت همگام‌سازی)
```

اول این شش عمل را کامل کن، بعد بقیه‌ی مقاصد. هر id که به `IMPLEMENTED` اضافه
می‌شود **باید** صفحه‌ی واقعی داشته باشد.

### B5 · انتقال داده (۵ → ۸)

- موجودیت‌ها: `supplier · employee · account + مانده‌ی افتتاحیه`
- **XLSX** فقط با parser ایزوله و اثبات‌شده. تا آن‌موقع تبلیغش نکن.
- **بازسازی رابطه** (§29): فاکتور ← مشتری، سطر ← کالا.
- **اعتبارسنجی حسابداری** (§32) قبل از هر موجودیت مالی.

⚠️ ورود مالی مستقیم با وسواس فوق‌العاده — وگرنه **حقیقت مالی دوم** ساخته می‌شود.
