# یک UI، یک قرارداد، دو میزبان

> ۲۱ سپتامبر ۲۰۲۶. این سند جایگزین هر توضیح قبلی درباره‌ی «UI موبایل» است.

```
                packages/app-shell          ← همان محصول، یک بار
                        │
                packages/app-bridge         ← HisabcheBridge (قرارداد)
                        │
          ┌─────────────┴─────────────┐
      Electron                  React Native
   (apps/desktop)               (apps/mobile)
   window.hisabche              window.hisabche
          │                            │
    Node / IPC                  Expo / Android / iOS
```

**UI هرگز نمی‌داند روی کدام میزبان است.** نام هیچ میزبانی در `packages/app-shell`
نیست — گارد `one-ui-two-hosts.test.ts` این را می‌گردد.

---

## چرا این کار شد

`packages/ui` با `div` و `className` نوشته شده. Electron آن را در Chromium رندر
می‌کند، برای همین ویندوز و وب همیشه یکی بودند. اپ موبایل React Native بود و در RN
اصلاً `div` وجود ندارد — پس ۲۵ صفحه و ۲۶ کامپوننت **نسخه‌ی سوم همان محصول** بودند.

نتیجه‌ی واقعی‌اش: برچسب‌ها فرق می‌کردند، ستون‌های جدول فرق می‌کردند، و چهار صفحه‌ی
وب (`/assistant`، `/operations`، `/stock-count`، `/domain/:id`) اصلاً روی ویندوز و
موبایل وجود نداشتند.

کشف کلیدی: رندرر دسکتاپ **صفر** ارجاع به Electron داشت. یعنی از روز اول قابل
اشتراک بود و فقط در جای اشتباهی (`apps/desktop/src`) نشسته بود.

---

## قواعد

**۱. صفحه‌ی جدید فقط در `packages/app-shell`.** هیچ میزبانی صفحه‌ی خودش را ندارد.
هر مسیری که وب دارد باید اینجا هم باشد — گارد `route-parity.test.ts` تمام
`apps/web/app/[lang]/(dashboard)` را می‌پیماید و مقایسه می‌کند.

**۲. قابلیت نیتیو جدید فقط در `HisabcheBridge`.** اگر متدی را فقط یک میزبان
می‌تواند پیاده کند، جایش در این رابط نیست. هر دو میزبان باید جواب بدهند — حتی اگر
جواب «این کار روی این دستگاه ممکن نیست» باشد.

**۳. هرگز `window.hisabche` را مستقیم صدا نزن.** از `bridge()` در
`packages/app-shell/src/shared/lib/bridge.ts` استفاده کن که `null` را هندل می‌کند
(تست‌ها و پیش‌نمایش مرورگر میزبان ندارند).

**۴. بیلد هم یکی است.** `packages/app-shell/vite.shell.mjs`. میزبان فقط مسیر خروجی
می‌دهد. اگر میزبانی شروع کند به تعریف alias خودش، UI دوباره دوشاخه شده است.

---

## تله‌هایی که در پیاده‌سازی خوردیم

⚠️ **WebView پستخانه دارد، نه کانال.** `contextBridge` تابع واقعی می‌دهد که Promise
برمی‌گرداند. WebView فقط `postMessage` رشته‌ای دارد. پس همان قرارداد با
correlation-id بازسازی شد (`webview-rpc.ts`): هر فراخوانی یک `id` می‌گیرد، Promise
زیر آن id پارک می‌شود، و میزبان با همان id جواب می‌دهد. **هر درخواست دقیقاً یک
پاسخ می‌گیرد** — خطا هم یک پاسخ است، نه سکوت؛ وگرنه Promise تا ابد معلق می‌ماند و
صفحه روی spinner می‌ایستد با کنسول ساکت.

⚠️ **نام متد از یک صفحه می‌آید، پس allow-list لازم است.** `WEBVIEW_METHODS`. همان
قاعده‌ای که `electron/main/ipc/register.ts` دارد.

⚠️ **پل باید قبل از محتوا تزریق شود.** `injectedJavaScriptBeforeContentLoaded`.
UI هنگام مقداردهی ماژول‌هایش تصمیم می‌گیرد که میزبان دارد یا نه؛ پلی که بعد از
اولین رندر نصب شود، پلی است که UI قبلاً نتیجه گرفته وجود ندارد — دقیقاً همان
اشتباه BUG-019 درباره‌ی توکن.

⚠️ **Metro فقط چیزی را کپی می‌کند که import شده.** بیلد عادی Vite کنار
`index.html` ۴۵ فایل می‌گذارد؛ هیچ‌کدام وارد اپ نمی‌شدند و صفحه با ۴۵ تا ۴۰۴
بالا می‌آمد، **بی‌صدا**. رفع: گزینه‌ی `singleFile` که JS/CSS/فونت را داخل یک
`index.html` inline می‌کند. فقط برای موبایل — Electron فایل‌سیستم واقعی دارد.

⚠️ **خروجی بیلد در git نیست.** `assets/shell/` در `.gitignore` است و EAS آن را در
`eas-build-post-install` می‌سازد. اگر commit شود، لحظه‌ای که کسی UI مشترک را عوض
کند بی‌صدا کهنه می‌شود و موبایل نسخه‌ی دیگری از محصول را می‌فرستد.

⚠️ **موتور آفلاین نیتیو می‌ماند.** اندروید هر لحظه WebView پس‌زمینه را می‌کشد و صفِ
فاکتورهای آفلاین باید دقیقاً از همان جان به در ببرد. `sync-runner` دیگر
`QueryClient` نمی‌گیرد — کشی که ممکن است صفحه‌اش دیگر وجود نداشته باشد — و به‌جایش
رویداد `outboxDrained` را به صفحه push می‌کند.

⚠️ **درخواست HTTP از میزبان می‌رود، نه از صفحه.** صفحه‌ای که از
`file://android_asset` سرو می‌شود origin تهی دارد؛ هر تماس با `api.hisabche.com`
از مبدأیی است که هیچ فهرست CORS ای نمی‌تواند نامش را ببرد. دسکتاپ هم به همین دلیل
HTTP را از main رد می‌کند.

## تصمیم‌هایی که گرفته نشده‌اند

**ارتقای Expo/RN.** مالک صریحاً گفت مهاجرت نسخه از مهاجرت معماری جداست.
`react-native-webview@13.8.6` نسخه‌ی سازگار با SDK 51 است و باندل واقعی تأییدش
کرد. New Architecture فعال نشده.

~~**`db.query` و `db.upsertMany` روی موبایل.**~~ ✅ انجام شد — موبایل حالا
`expo-sqlite` دارد و همان SQL دسکتاپ را اجرا می‌کند. بخش «مسیر داده» پایین‌تر.
⚠️ ولی وقتی کش **باز نشود** هنوز خطا می‌دهد و لیست خالی برنمی‌گرداند: «کش ندارم»
با «این workspace کالایی ندارد» یکی نیست (§۷٫۳).

**`print.escPos` و `files.import` روی موبایل.** چاپگر رسید و انتخاب فایل به
دسترسی‌ای نیاز دارند که این بیلد ندارد. هر دو خطا می‌دهند، نه `true` دروغین.

## مسیر داده تا سرور — کدام راه، و چرا

```
  SQLite دسکتاپ            SQLite موبایل
  (better-sqlite3)          (expo-sqlite)
        │                         │
        └──── window.hisabche.db ─┘
                    │
              sync_queue (یکی، در SQLite)
                    │
              routeFor()  ← @hisabche/app-bridge
              ┌─────┴─────┐
     مسیر دامنه         مسیر نسخه‌دار
  POST /api/invoices   POST /api/sync/push
  POST /api/transactions
        │                     │
  موجودی + دفتر +       expectedVersion +
  شماره‌گذاری +          ثبت conflict
  محاسبه از خطوط         (بدون منطق دامنه)
        │                     │
        └────── Fastify ──────┘
                    │
                 Supabase
```

**هیچ کلاینتی مستقیم به Supabase نمی‌نویسد.** شش فایل `@supabase/supabase-js`
دارند و همه realtime یا presence‌اند — تأیید شده با grep روی کل `packages` و
`apps`.

### قانون مرز

> هر چیزی که `total`، `paid_amount`، `status`، `amount`، موجودی یا دفتر را
> تغییر می‌دهد → **فقط** سرویس دامنه.
> مسیر نسخه‌دار فقط برای فیلد توصیفی: نام، تلفن، آدرس، بارکد، دسته، یادداشت.

⚠️ **چرا این مرز حیاتی است:** `/api/sync/push` ردیف را با
`supabase.from(table).insert()` می‌نویسد. فاکتوری که از آن راه برود، فاکتوری است
که هیچ کالایی از انبار خارج نکرده، هیچ درآمدی ثبت نکرده و شماره نگرفته — و سند و
دفتر برای همیشه با هم اختلاف دارند.

قانون در `packages/app-bridge/src/push-routing.ts` است و **دو طرفه** اجرا می‌شود:
کلاینت با `routeFor()` مسیر را انتخاب می‌کند، و سرور با `WRITABLE` باریک‌شده
اصلاً اجازه‌ی نوشتن فیلد مالی از آن راه را نمی‌دهد. سروری که به کلاینتش اعتماد
کند، قانونی ندارد.

### تله‌های این لایه

⚠️ **`CREATE TABLE IF NOT EXISTS` migration نیست.** روی دستگاهی که جدول دارد
هیچ کاری نمی‌کند، پس ستون جدید فقط برای نصب‌های تازه وجود دارد. `schema_version`
در `meta` از قبل نوشته می‌شد و **هیچ‌کس نمی‌خواندش**؛ حالا `migrationsFrom()`
می‌خواند.

⚠️ **`transaction` کلمه‌ی کلیدی SQL است.** یکی از جدول‌های کش همین نام را دارد و
`ALTER TABLE transaction` خطای نحوی می‌دهد. گارد `local-migrations.test.ts`
چهل کلمه‌ی رزرو را روی همه‌ی جدول‌ها چک می‌کند.

⚠️ **موجودیت طبقه‌بندی‌نشده امن نیست.** اولین نسخه‌ی `routeFor` هر جدول ناشناخته
را به مسیر سریع می‌فرستاد؛ یعنی جدولی که سال بعد اضافه شود، در اولین ویرایش از
کنار دامنه رد می‌شد. حالا `DESCRIPTIVE_ENTITIES` یک allow-list است و بقیه همه
اعتبارسنجی می‌شوند.

⚠️ **پول حذف نمی‌شود، معکوس می‌شود.** `DELETE /api/transactions/:id` ردیف را
مستقیم پاک می‌کرد: `paid_amount` فاکتور دست‌نخورده می‌ماند (فاکتورِ «پرداخت‌شده»
بدون پرداخت)، سند دفتر می‌ماند، و رد حسابرسی هم می‌رفت چون رکورد **همان ردیفی بود
که پاک شد**. حالا به `cancelPayment` می‌رود.

⚠️ **خروج از حساب ≠ تعویض workspace.** `setWorkspace` وقتی نوشته‌ی ارسال‌نشده
هست **رد می‌کند**؛ خروج از حساب نمی‌تواند رد کند، پس فقط کشِ خواندن را پاک
می‌کند و صف را نگه می‌دارد — دور ریختن فاکتور ارسال‌نشده برای مرتب‌کردن کش یعنی
نابودکردن تنها نسخه‌ی آن (§12).
