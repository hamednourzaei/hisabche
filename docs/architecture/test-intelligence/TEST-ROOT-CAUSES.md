# ۵۰ علت اندازه‌گیری‌شدهٔ کندی تست‌ها

> **تاریخ اندازه‌گیری:** ۱۶ نوامبر ۲۰۲۶ · **دستگاه:** Windows، ۱۶ هستهٔ منطقی، ۴۰GB RAM
> **منبع هر عدد:** `vitest --reporter=json` (زمان هر تست)، نه تخمین.
> **قاعدهٔ خواندن:** «ms» = زمان خودِ تست در همان اجرا. در اجرای موازی، این عدد شامل
> رقابت CPU با فایل‌های دیگر هم هست؛ بنابراین مجموع msها با زمان دیوار یکی نیست.

سه واقعیت که همهٔ فهرست زیر از آن بیرون می‌آید:

1. **backend:** ۵۶ تست (۱٪) ۵۵٪ کل زمان تست‌ها را می‌برند؛ میانهٔ تست ۱٫۳ms است.
2. **تست اولِ هر فایل ۴۹٫۶٪ زمان backend** است (۷۷٬۴۴۱ms) — یعنی هزینهٔ ساخت گراف
   ماژول در هر فایل، نه هزینهٔ assertion.
3. **ui:** یک تست تنها ۴۸٫۷٪ زمان تست‌هاست؛ میانهٔ تست ۰ms و p95 آن ۲۹ms.

## فهرست ۵۰ علت

ستون «وضعیت» فقط با اجرای واقعی پر شده است: `اصلاح‌شد` = قبل/بعد اندازه‌گیری شد،
`باز` = علت شناسایی شد ولی تغییر نکرد، `ذاتی` = کار واقعیِ تست است و نباید حذف شود.

## سه خانوادهٔ ریشه‌ای (خلاصهٔ علت‌ها، نه تکرارشان)

1. **خواندن تکراری همان فایل‌ها** (ردیف ۱، ۲، ۵، ۱۵، ۴۱، ۵۱–۵۸): الگوی «برای هر ردیف/قاعده/جدول،
   کل درخت را از نو بخوان». این خانواده با یک کش درون‌فرایندیِ معتبر حل می‌شود و هیچ assertion
   را تغییر نمی‌دهد.
2. **spawn پروسه برای کاری که می‌شود یک بار انجام داد** (ردیف ۳، ۴، ۶–۱۲): هر `spawnSync` حدود
   ۳۵ms فقط برای بالا آمدن node است، به‌علاوهٔ کار مولد.
3. **ایزوله‌بودن هر فایل تست** (ردیف ۲۴–۴۵، ۵۹): ۴۹٫۶٪ زمان backend، ساخت گراف ماژول برای هر فایل
   است. این هزینه ذاتیِ ایزوله‌بودن است و «رفع» آن یعنی به‌هم‌ریختن ایزولاسیون — انجام نشد.
