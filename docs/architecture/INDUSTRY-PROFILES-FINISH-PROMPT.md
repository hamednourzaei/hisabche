# پرامپت اجرایی — بستن کامل «پروفایل صنف» روی همه‌ی پلتفرم‌ها (آخرین دور)

> ادامه‌ی `INDUSTRY-PROFILES-AGENT-PROMPT.md`، با قیدِ `EVIDENCE-FIRST-SUPPLEMENT-PROMPT.md` (اول شواهد، بعد کد).
> گزارش دور قبل: `IMPLEMENTED_NOT_LIVE_VERIFIED` — هسته‌ی `validation` سبز (۵۳۰ تست)، ولی چند چیز **ساخته نشد** و چند ادعا **هنوز با مسیر واقعی اثبات نشده**.
> هدف این دور: **بک‌اند، وب، ویندوز، موبایل، آنلاین و آفلاین همه با هم تمام، دیباگ‌شده و با اجرای واقعی تأییدشده.** هیچ بخشی «بعداً».

## ۰. قواعد ثابت

1. **commit و push نکن** (مالک خودش). subagent نساز. وسط کار نپرس «کدام فاز». DDL مستقیم روی Supabase ممنوع (فقط فایل `docs/*.sql` + VERIFY + تست دوبار اجرا؛ `PENDING HUMAN CONFIRMATION`).
2. **کار مالک را برنگردان:** working tree شامل تغییرات تأییدشده‌ی قبلی است (**قرارداد فیلتر** `filter-contract.ts` + `flagFilter` در سرور و موتور، `fetchProducts/fetchCustomers` از طریق موتور محلی، `isUnsetValue` در درگاه موتور، تست‌های `list-filter-contract-*`، فیکس `site-footer`، پیام «نقشه‌ی قفسه آفلاین»). به آنها دست نزن مگر باگ ثابت‌شده؛ قبل از هر `git checkout --` diff را ببین.
3. **اول شواهد:** هر ادعا با تست/اجرا/`فایل:خط`. گزارش قبلی خودش «Offline پروفایل generic می‌گیرد»، «سوئیت کامل ui/backend اجرا نشد»، «بیلد/Electron/Hermes اجرا نشد» را گفته — همه‌ی اینها در این دور بسته می‌شوند.
4. سوئیت‌ها **پشت سر هم** (موازی گاردهای درخت‌خوان را timeout می‌کند). فقط `pnpm exec vitest run` / `npx jest` خود پروژه معتبر است؛ harness کناری مدرک نیست.
5. **مسیر واقعی، نه فقط mock.** برای هر تغییر UI/IPC در **برنامه‌ی واقعی ویندوز** نگاه کن (computer-use، با اجازه‌ی مالک؛ برنامه همین الان نصب است). دیتابیس زنده‌ی برنامه `%APPDATA%\@hisabche\desktop\hisabche.db` است — فقط **کپی**اش را بخوان و پس از کار کپی را پاک کن؛ نسخه‌ی نصب‌شده را با تاریخ `app.asar` بسنج.
6. محیط این ماشین: `%TEMP%` برای esbuild/initdb `Access is denied` می‌دهد → برای هر بیلد `TEMP`/`TMP` را روی `C:\Users\hamed\Desktop\hisabche\.pgtest\tmp` بگذار؛ ۸۰ فایل `|pg|` بک‌اند به‌خاطر محیط می‌ریزند (جدا بشمار، با شکست محصول قاطی نکن)؛ Defender «Neshta» فعال گزارش کرده (فایل بیلد را برای پخش روی دستگاه تمیز اسکن کن).
7. شکل داده را از **handler واقعی** بخوان: `engine.request` پارامتر را در `params` می‌گیرد (نه `query`)؛ `/suppliers` آرایه‌ی خالص است؛ هر ویرایشِ route شماره‌ی خطِ شواهدِ CSV را عوض می‌کند → `node scripts/generate-capability-matrix-csv.mjs`؛ formatter خودکارِ hook گاردهای `toContain` روی یک خط بلند را می‌شکند (گارد باید عناصر را بسنجد).

## ۲. فاز ۱ — Audit دوباره‌ی ادعاهای گزارش قبلی (قبل از هر کد)

بدون اعتماد به گزارش، اینها را اجرا و ثبت کن (`docs/architecture/industry/VERIFICATION-LOG.md` به‌روز):

1. `git status` و `git diff --stat`: دقیقاً چه چیزی تغییر کرده؛ تغییر بی‌ربطی هست؟
2. `setRowProduct` و `rowQuantity`: **همه‌ی مصرف‌کننده‌های** `quantity` در فاکتور (بک‌اند `InvoiceService`، موتور `routes/invoices.ts`، چاپ، sync/outbox، گزارش سود، `useOversoldLines` چک موجودی، اسکنر بارکد `planScan`، فاکتور تکراری/`automation`، ورود فایل `invoice-import.domain.ts`). جدول «مصرف‌کننده ← رفتار قبل ← رفتار بعد ← ریسک». هر کدام که واحد را نمی‌داند باید همان قاعده‌ی مشترک را بخواند.
3. «quantity خالی فقط در واحد اندازه‌گیری `0` می‌شود؛ واحد شمارشی `1`»: اثرش روی کاربرانی که قبلاً با واحد `gram` فاکتور می‌زدند (پیش‌فرض ۱ گرم) و روی اسکنر/ترازو (`planScan` و برچسب ترازو که وزن را می‌دهد).
4. `applyInvoiceDefaults`/`initColumns`: کاربر قدیمی با چیدمان ذخیره‌شده **هیچ تغییری** نبیند (`columnsInitialised`)؛ تست با store ذخیره‌شده‌ی نسخه‌ی قبل.
5. onboarding: «ذخیره‌ی واقعی روی سرور + خطای ذخیره» — با HTTP واقعی و در حالت شکست شبکه چه می‌شود؟ کاربر گیر نکند؛ آفلاین چه؟
6. گارد AST «`businessType === '…'`»: بیرون از رجیستری هیچ شاخه‌ی صنف نیست (grep مستقل هم بزن؛ `switch`، `includes('gold')`، مقایسه‌ی رشته‌ی comma).
7. شمار واقعی: ۶۱ کلید صنف در رجیستری در برابر onboarding (`industry-profile-registry.test.ts`) و `JOURNEY_INDUSTRIES` و ۴۹ صنف ریل؛ کلیدهای بی‌صاحب.

## ۳. فاز ۲ — پیاده‌سازی (به ترتیب A → B → C → D → F)

هر بند: **تست رگرسیون قرمز با کد خراب** (injection) ← فیکس کوچک در مرز درست ← سبز ← تست‌های همسایه.

- A را اول انجام بده؛ اگر ناهمخوانی یافتی، همان‌جا بایست و درست کن (هر چیزِ بعد روی آن سوار است).
- B: هر تغییر `local-schema.ts` = بررسی `desktop/…/migrations.test.ts` و معادل موبایل؛ `GET` پاسخ موتور شامل صنف؛ `PATCH` آفلاین؛ ماتریس آفلاین؛ `unwired-capability` سبز.
- هر کلید i18n تازه در **هر سه** locale (`fa`/`af`/`en`، واژه‌نامه‌ی دری)؛ `t()` روی کلید ناموجود صفحه را می‌اندازد. در دسکتاپ/موبایل `t.has` وجود ندارد (`translateOr`).
- UI مشترک: ناوبری فقط `useLocalePush`/`localizePath`؛ هر صفحه‌ی وب → route در `app-shell/src/app/app.tsx`؛ جدول = `DataTable`، انتخاب = `SelectField`؛ رنگ فقط توکن؛ RTL با `ms-/me-`.

## ۵. فاز ۴ — بیلد و **برنامه‌ی واقعی** (فقط بعد از بند ۴ سبز)

1. `cd apps/web && pnpm run build` (سبز) — سپس بازرسی HTTP واقعی روی ۳۱۱۱ اگر لازم شد.
2. ویندوز: `electron-vite build` سپس `electron-builder --win --publish never -c.electronDist=node_modules/electron/dist` با `TEMP/TMP` روی `.pgtest/tmp`؛ تاریخ `dist/Hisabche-0.0.1-setup.exe` را با ساعت فعلی بسنج.
3. اندروید: `cd apps/mobile && pnpm run android:release` (اول shell، بعد Gradle)؛ **تاریخ APK** را بسنج، نه پیام Gradle.
4. **در برنامه‌ی واقعی ویندوز (computer-use)، دو حالت آنلاین/آفلاین:** (الف) onboarding/تنظیمات صنف را عوض کن؛ (ب) کالای `gram` با موجودی ۱۵ بساز؛ (ج) فاکتور فروش ۱۵ گرم ← جمع، موجودی بعد، سند، سود؛ (د) کالای شمارشی (لیوان) فاکتور ← رفتار «تعداد ۱» حفظ؛ (هـ) کاربر قدیمی با چیدمان ذخیره‌شده هیچ تغییری نبیند. اسکرین‌شات‌ها را ذخیره و مسیر بده. اگر نشد، دقیقاً چرا (نه «امکان‌پذیر نبود»).
5. موبایل: امولاتور/دستگاه **اگر در دسترس** نیست، صریح `IMPLEMENTED_NOT_LIVE_VERIFIED` بنویس؛ شبیه‌سازی Jest را «تست دستگاه» ننام.

## ۷. وقتی باید بایستی

دو تفسیر با نتیجه‌ی مالی متفاوت؛ منبع حقیقت یک مقدار پیدا نمی‌شود؛ مهاجرت دستگاه ممکن است داده‌ی قدیمی را خراب کند؛ تغییر مجوز لازم می‌شود. آن‌گاه فقط همان مسیر متوقف و ثبت شود (پیامد هر گزینه، کوچک‌ترین تصمیم لازم از مالک، پیش‌فرض امن)؛ بقیه‌ی کارها ادامه یابد. سؤال کلی نپرس.
