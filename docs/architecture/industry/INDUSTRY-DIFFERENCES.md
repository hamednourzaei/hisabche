## ۱. آیا پروفایل صنف واقعاً وجود دارد؟

**بله، به‌صورت یک پروفایل مشتق‌شده — نه جدول دوم.** منبع حقیقت همان `profiles.business_types` است که از قبل وجود داشت.
فایل رجیستری: `packages/validation/src/schemas/industry-profiles.ts` (کل فایل ۴۵۵ خط).
تابع حل‌کننده: `resolveBusinessProfile(types, explicitPrimary)` در همان فایل، خطوط ۴۰۳–۴۵۵.
رجیستری قابلیت‌ها: `packages/validation/src/schemas/business-capabilities.ts`.

اعداد مشتق‌شده از کد (خروجی `node scripts/industry/generate-industry-diff.mjs --check` و جدول ماشینی):

| سنجه                               | مقدار                                             |
| ---------------------------------- | ------------------------------------------------- |
| کلیدهای صنف در رجیستری             | ۶۱                                                |
| قابل انتخاب در onboarding          | ۶۱                                                |
| پروفایل تخصصی                      | ۱۳                                                |
| فقط پایهٔ عمومی                    | ۴۸                                                |
| تطابق دقیق با `JOURNEY_INDUSTRIES` | ۱۴                                                |
| قابلیت‌های `available`             | ۳ (`measurement`، `weight_pricing`، `multi_unit`) |

> ⚠️ سه قابلیت دیگر (`gold_purity` و مانند آن) وضعیت `planned` دارند و حل‌کننده آن‌ها را به هیچ پروفایلی متصل نمی‌کند.
> بنابراین «طلا و جواهر» در حسابچه **محاسبهٔ عیار یا اجرت ندارد**؛ فقط وزن/واحد و ضرب مقدار در قیمت واحد دارد.

## ۱۱. ریسک‌ها و ناشناخته‌ها

1. **تفاوت تبدیل واحد آفلاین/آنلاین** (بخش ۶) — می‌تواند موجودی را بین دو دستگاه ناهمخوان کند.
2. **افزودن ستون وزن به کاربران قدیمی** — فقط وقتی رخ می‌دهد که چیدمان ذخیره‌شده نداشته باشند؛ تست واحد برای مهاجرت چیدمان ذخیره‌شده وجود دارد اما تست HTTP/مرورگر نه.
3. **ذخیرهٔ صنف آفلاین** — بدون ستون، انتخاب صنف در دستگاه گم می‌شود.
4. **ویرایش صنف در تنظیمات** — وجود ندارد؛ کاربر باید onboarding را دوباره طی کند یا API را مستقیم صدا بزند.
5. **بدون تأیید زنده** — هیچ اسکرین‌شات یا اجرای Electron/Hermes/دستگاه واقعی نداریم.
