# Universal-core gap analysis

Decisions use exactly: `IMPLEMENT_NOW` · `IMPLEMENT_LATER` · `ALREADY_SUPPORTED` · `NOT_JUSTIFIED` · `BLOCKED_BY_EXTERNAL_DEPENDENCY`.

Evidence for every row is in `INDUSTRY-COVERAGE-TABLE.md` (resolved file:line). External sources are listed there too, with their kind — most are vendor pages, so they show what the trade _claims to need_, not a legal obligation.

## Why only four rows are `IMPLEMENT_NOW`

The largest gaps (variants, area, roll units, trips, ticketing) each need a **new data model** that touches the schema, the offline engine’s `SCHEMA_VERSION`, the invoice builder and sync. Doing that inside a working tree where another change set is mid-flight, with no owner decision on the accounting policy behind several of them, would trade a visible gap for a silent data-integrity risk. They are scoped, not skipped: each has a smallest-correct implementation and the test that would close it.

## Risk notes for the deferred P0/P1 rows

- **G-05 variants** — touches `products`, the invoice grid, offline schema and sync keys. Must be additive (a template product + variant rows) and must not reinterpret existing products. Backfill is forbidden (guardrail §12).
- **G-08 credit** — enforcing a limit retroactively blocks sales that work today. Default must be «advise», chosen by the owner.
- **G-10** — selling a serial that sync later shows already sold is a conflict class the offline engine has no rule for yet.
