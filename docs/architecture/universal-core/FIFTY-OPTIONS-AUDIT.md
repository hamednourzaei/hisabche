## 1. Duplicates already created by the in-flight `universal-core` bundle

An agent is currently adding `backend/src/services/universal-core/universal-core.service.ts` (748 lines, 12 domains in one class), `backend/src/routes/universal-core.routes.ts`, `packages/api/src/hooks/universal-core.ts`, `packages/app-bridge/src/local-universal-core-schema.ts`, `packages/local-engine/src/routes/universal-core.ts`, and `docs/universal-core-migration.sql` (18 tables). Measured against the repository, three of those tables **duplicate existing ones**:

| In-flight table   | Existing owner                                                                            | Decision                                                                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pack_barcodes`   | `product_barcodes` (has `unit`)                                                           | **Delete** `pack_barcodes`, its route/service/engine table. Scanning a case = look up `product_barcodes.unit` and call `toBaseQuantity`                                 |
| `product_serials` | `stock_serials` + `stock_batches` (`traceability-migration.sql`, `services/traceability`) | **Delete** `product_serials`. Wire invoice creation to the existing consume path                                                                                        |
| `vehicle_units`   | `stock_serials` (serial = chassis/VIN, cost, warehouse, received_on)                      | Do **not** keep a parallel stock table. Keep only an _attribute_ table `vehicle_attributes(serial_id, make, model, year, colour, odometer)` keyed to `stock_serials.id` |

Two structural problems: (a) one 748-line class and one 483-line route file mixing 12 domains breaks the repository convention (one folder per domain under `services/`), and (b) an entity owned by two modules is the pattern CLAUDE.md §2 (G2) forbids. Fix: split by domain into the folders in §3 and delete the three duplicates **before** adding anything else.

## 3. Where each thing goes (repository placement, so nothing is created twice)

Repository convention, from the code: rule in `packages/validation/src/schemas/<x>.domain.ts` (so server **and** engine import it) → service in `backend/src/services/<domain>/` → route in `backend/src/routes/<domain>.routes.ts` → engine route in `packages/local-engine/src/routes/<domain>.ts` + SQLite table in `packages/app-bridge/src/local-schema.ts` → hook in `packages/api/src/hooks/<domain>.ts` → screen as a section of an existing hub in `packages/ui/src/components/ui/<domain>/` → matrix row in `packages/validation/src/schemas/offline-endpoint-matrix.ts` → keys in `packages/i18n/messages/{fa,af,en}/common.json` → migration + VERIFY + `*.pg.test.ts`.

Placement rules that stop duplicates: **one table per entity** (search `docs/*.sql` for the name and the concept first); **money moves only through** `InvoiceService`, `PaymentsService`, `ledger.postDocument`; **no entity owned by two modules**; **a new capability is a tab or section of an existing hub**, not a route (CLAUDE.md §8).
