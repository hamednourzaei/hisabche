## Compatibility Window Rules (Verified by `compatibility-matrix.test.ts`)

| Scenario                                                           | Expected Outcome                     | Rationale                                                                                                                   |
| ------------------------------------------------------------------ | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Old Bootstrap + New Core (within `minBootstrap`..`maxBootstrap`)   | **WORKS**                            | Core remains compatible with existing IPC/native bridge.                                                                    |
| Old Bootstrap + New Core (`core.minBootstrap > bootstrap.version`) | **REFUSE**                           | Core requires newer native IPC/permissions; routes user to shell/binary update.                                             |
| New Bootstrap + Old Core (within `maxCore` / `minCore`)            | **WORKS**                            | Backward-compatible native host supports existing Core slot.                                                                |
| Old Core + New Module (`module.requiredCore` satisfied)            | **WORKS**                            | Module loads cleanly against typed extension contract.                                                                      |
| Old Core + New Module (`module.requiredCore` unsatisfied)          | **REFUSE**                           | Module rejected before staging/activation; previous module stays active.                                                    |
| New Core + Old Module (incompatible with new Core)                 | **REFUSE_OR_DISABLE_MODULE**         | Core never crashes; incompatible optional module disabled without deleting its data (`I13`).                                |
| Old API + New Client (missing required API contract)               | **REFUSE_UPDATE / DEGRADED_OFFLINE** | Client refuses unsafe activation or stays in offline-safe mode.                                                             |
| New API + Old Client (above `minSupportedVersion`)                 | **WORKS**                            | Expand-only API preserves legacy fields/endpoints.                                                                          |
| New API + Old Client (below `minSupportedVersion`)                 | **STRUCTURED_UPGRADE_REQUIRED**      | Server returns `UPGRADE_REQUIRED` with target version; client shows actionable banner and keeps offline work intact (`I8`). |
| Old Local Schema + New Runtime                                     | **MIGRATE_AFTER_SAFETY_CHECK**       | Runs additive SQLite migration only when no active financial transaction is open (`I11`).                                   |
| New Local Schema + Old Runtime (e.g., unsafe rollback target)      | **REFUSE_ROLLBACK → SAFE_MODE**      | Older runtime refuses to open newer local DB destructively; enters safe mode (`§8.4`, `§10`).                               |
