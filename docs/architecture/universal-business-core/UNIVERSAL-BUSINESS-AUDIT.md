### F-02 — A competing command envelope and an unused offline-lease domain **FAILED** (law §8: "do not create a competing envelope")

`packages/validation/src/schemas/universal-core/command-envelope.ts` (12 exports) and `packages/validation/src/schemas/universal-core/offline-lease.domain.ts` (both removed in M1.0, §8) had **zero consumers**
outside their own tests and the barrel file (measured with `git grep -w` on every exported name: all 12 give 0).
The project already has a command model — the durable outbox row built by `buildEnqueue({entity, operation, clientId,
payload, userId, workspaceId})` plus the `Idempotency-Key` header. The new envelope is a second, unconnected shape.
Nothing refuses an offline cash refund _because of a lease_: refunds are blocked by the matrix row
`POST /invoices/:x/returns/:x/refunds → online_required`, and there is no local refund route at all. The "S2.3 Offline Refund
Lease PASSED" claim is a rule that exists and that nobody calls (CLAUDE.md §7.1).

### F-10 — The "parity harness" compared a function with itself **FAILED** (test that cannot fail)

`unified-core-parity-harness.ts` (removed in M1.0) claimed to execute a return against "the shared core, a local adapter and a remote adapter" and
assert equivalence. Reading it: the "local adapter" re-called `calculateReturnDocument` and `computeReturnDeductions` — the same functions as
the "core" — and the "remote adapter" copied the core's output object. It never touched `packages/local-engine`, SQLite, `invoice_return_create`
or the backend service, so its `identical: true` was true by construction. The earlier reports quoted its single passing test ("Parity harness 1/1")
as proof of Gate C. The only parity evidence that exists is the 19 scenarios in
`backend/src/__tests__/helpers/invoice-return-05-scenarios.ts`, which run the real migration SQL on a real Postgres engine; the local side has none.

## 12. F-11 — cancelling on the device posts a reversal (product code)

**Status `IMPLEMENTED_NOT_LIVE_VERIFIED`** (was open at the end of M1.2; executed after M1.3 as the owner asked).

Cause: `packages/local-engine/src/routes/invoices.ts` (cancel) and `packages/local-engine/src/routes/payments.ts` (cancel) flipped the original entry to `reversed` without a
reversal entry. A report that skips `reversed` rows then lost the entry for the whole period it fell in, and an entry in a closed period was edited after closing.

manual journal reversal (whose inline copy was removed). A closed day refuses the whole cancel with 409 `ACCOUNTING_PERIOD_LOCKED` inside the transaction, so nothing is left half done; an entry that
is not `posted` yields `null` (no second reversal).

Effects: reports — the original stays in its period, the reversal appears from its own date on, the document nets to zero (tested). Audit trail — two rows linked by `reversal_of`. Sync — the cancel
itself is still queued (`payment` delete / invoice cancel); the server posts its own reversal when it applies it, exactly as before for the original entries (local ledger rows are the device's own view).
Tests: `packages/local-engine/src/__tests__/cancel-posts-reversal.test.ts` (4, red before); `packages/local-engine/src/__tests__/period-lock-parity.test.ts` still green.
Open: cancelling an invoice reverses **every** allocated payment's entry even when that payment also settled other invoices — a pre-existing behaviour, not changed here (needs the server rule read first).

1. two DEVICES each consuming the last credit offline: the server refuses the second on sync and the command becomes a visible `REJECTED` entry, but that device's session stays «delivered». Undoing the local delivery versus asking the person is a policy decision — `NEEDS_OWNER_DECISION`.
2. the SQL concurrency scenario ran on PGlite (a single connection, so sequential). True parallel locking needs `backend/src/__tests__/service-delivery-02.pg.test.ts` on a machine whose embedded Postgres can start — `BLOCKED_EXTERNAL`.
3. no golden-vector corpus is shared by the domain and the SQL function: the same rule list is asserted separately on each (12 SQL scenarios, domain tests).

### 18.3 New defect found by M5.0 work: a package GRANT travelled to the CONSUME endpoint

`packages/local-engine/src/routes/invoices.ts` queued a `package_credit_ledger` command for the grant of an offline package sale, and `packages/app-shell/src/features/sync/sync-engine.ts` sent every ledger entry that was not REVERSAL / EXPIRE / ADJUSTMENT to `/package-credits/consume`: a grant of 10 units was sent as a consume of 10 units (it spent the credit the invoice had just granted, or was refused and left device and server disagreeing). **Fixed:** the device keeps the local grant (usable offline) and queues the invoice only — the server grants the credit when it saves the invoice line; the sync engine now refuses a GRANT command permanently and visibly (`PACKAGE_GRANT_TRAVELS_WITH_THE_INVOICE`) instead of consuming. Tests: `packages/local-engine/src/__tests__/package-grant-outbox.test.ts` (red first), the jest case in `packages/app-shell/src/features/sync/__tests__/sync-scenarios.test.ts`, and the older ledger test that locked the old behaviour was rewritten with the new decision.
**Open, recorded (not changed):** the server grants a package line in a SECOND call after the invoice is saved and only logs a failure (`grantPackageCreditsForInvoice` in `backend/src/services/invoice.service.ts`): a paid package can exist with no credit. The instrument below counts them. The fix is to grant inside the invoice transaction — a change to the invoice write path that belongs to its own slice with the owner's go.
