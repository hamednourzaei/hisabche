### SLICE A — deferred revenue, traceable per GRANT (M5-1, M5-4, B2-4)

- **A1** Add account role deferred revenue (a liability) via the five-file change.
- **A2 Posting rule — one function.** Extend `invoiceLedgerLines` (`packages/validation/src/schemas/invoice-posting.domain.ts`) with an optional deferred amount (books currency, net of tax, package lines, after discount): debit receivable full total; credit deferred revenue; credit sales for the remaining net; credit tax unchanged (M5-4); existing COGS lines. Without it the output is byte-identical (golden vectors incl. tax present/absent, zero net, no tax account). Server (`invoice.service.ts` near `:3259`) and device (`packages/local-engine/src/routes/invoices.ts`) call ONE shared helper using `inBooksCurrency` at the invoice's frozen rate. **One journal entry per invoice** — per-GRANT traceability is carried by the allocation data, not by extra journal entries.
- **A3 Per-GRANT memory.** The GRANT row stores its own deferred amount (books currency, net; NULL = sold before the cut-over = never released, **no backfill**, legacy liability reported as unknown, never zero). The journal credit and the GRANT amounts come from the SAME helper, so `Σ GRANT deferred = deferred credit of the invoice` always (reconciliation block in `docs/FINDING-package-credit-liability.sql`: per invoice, any difference is a finding).
- **A4 Allocation (C4).** In Phase 1 pick the smallest shape that lets every CONSUME and REVERSAL point to the GRANTs it drew from with quantity and released amount (proposed: allocation rows keyed consume/reversal entry + GRANT, written by the same functions, unique per pair, append-only, forward-only trigger). One pure function in `packages/validation` allocates a consume over valid GRANTs in the deterministic order (assumption 1), skips expired/suspended/not-yet-valid ones, never releases more than a GRANT's remaining deferred amount, releases a GRANT's exact remainder on its last unit (no rounding drift), and a reversal returns exactly what the original allocation released to the same GRANTs. Legacy (NULL) GRANTs consume in order and release nothing. Golden vectors: single GRANT; two GRANTs at different prices; legacy then new; one consume spanning two GRANTs; partial last unit; reversal; non-divisible amounts; expired GRANT skipped.
- **A5 Activation (B2-1).** The first valid CONSUME against a GRANT sets its activation date and end date once, server-side, immutable (forward-only trigger); an offline command carries the session date and the server validates it (assumption 2 / C3); a retry changes nothing. Same pure function on the device for display and pre-check; the server decides.
- **A6 Release at delivery.** New migration replacing `service_delivery_deliver` (guard the older definition in `docs/service-delivery-02-atomic-migration.sql`): for a package_credit settlement allocate (A4) and in the SAME transaction post ONE journal entry — debit deferred revenue, credit sales for the total released — dated the session date through `accounting_post_journal_entry` (read its signature and period-lock behaviour first), source type service_delivery, source id = the session id (replay-safe).
