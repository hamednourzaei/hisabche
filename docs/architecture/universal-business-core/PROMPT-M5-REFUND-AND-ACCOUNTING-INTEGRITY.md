## 4. Project invariants that apply to every line you write

- **`workspace_id` is the only security boundary.** `user_id` says who acted and is never a filter. Services take `TenancyContext`. Role from `request.tenancy.role`, never `request.userRole`. Every `.eq('id', …)` on a tenant table also has `.eq('workspace_id', …)`. Rows with `workspace_id IS NULL` are never written from inside a business.
- **Money is integer minor units**, no float in any money path; the server derives amounts from lines, never trusts the client. A fixture that touches money has **at least two currencies**; the books currency comes from `baseCurrencyOf`; no hard-coded `AFN` (guard `no-hardcoded-currency`). A sum without a currency is silently wrong.
- **No multi-table write from Node.** supabase-js has no transactions: multi-table writes are a Postgres function called with `.rpc()`. **No compensating DELETE.** The package-credit ledger and the journal are append-only: corrections are new entries that reference the original; the database refuses UPDATE/DELETE (trigger) — keep that true. The device ledger is not trigger-protected (the pull upserts it): do not rely on it, and do not add a trigger that would break pull.
- **A new account role is a five-file change that must land together:** the `accounts.role` CHECK in SQL, `packages/validation/src/schemas/standard-accounts.ts`, the labels in `fa/af/en` `common.json`, `packages/ui/src/lib/accounting/account-name.ts`, and the local seed/ensure path (`ensureAccountsForRoles` / `ensureDefaultAccounts`). Missing one is the known trap. A role that existing workspaces do not have must be **created on first use**, never assumed.
- **Fiscal lock:** a posting dated inside a closed period is refused whole (`ACCOUNTING_PERIOD_LOCKED`), inside the same transaction, before the first write. Reversal is a new entry dated today (or the stated date), checked against the lock.
- **One reference rule, many adapters.** A rule written in TypeScript (`packages/validation`), plpgsql and SQLite is _one rule with golden vectors_, not three. Before writing a second copy, extend the existing function. A closed-list guard must be edited when its list grows (never loosened).
- **Idempotency identity = the document** (session id, return id, entry id), never the HTTP header. The device and the server must name the **same ledger fact** with the same id. Outbox keys are distinct per command (`<id>`, `<id>-deliver`, …) because `buildEnqueue` upserts on `client_id`.
- **Offline is a mode of the same product** (lesson 227): every endpoint the client calls has a row in `offline-endpoint-matrix.ts` (`available | online_required | not_supported`) and a feature in `feature-registry.ts`; refunds of money stay `online_required` (OD-1). A dialog that needs the server renders `<CloudRequiredNotice />`, never a 501.
- **Permissions:** server `requireCapability` on every write route (guard `write-routes-have-a-capability.test.ts`: the ledger there only shrinks); the device mirrors the lowest role (`viewer-cannot-write.test.ts`). **Industry/business type is never a security boundary.** Hiding a button is never the control.
- **UI** (if any): `packages/ui` only; hub tab not a new route; `DataTable`, `SelectField`, `HubTabs`/`SegmentedControl`; `t()` throws on a missing key — add to all three locales; logical CSS only; tokens only; code-keyed server messages, never a server sentence in `t()`; unknown is `null`, not `0`; `placeholderData: []` is banned.
- **Database work is documents, not actions.** Write additive + idempotent `docs/<name>-migration.sql` with a rollback block and a separate `VERIFY-<name>.sql` (one row of booleans + counts of legacy rows that break a new rule; old rows are counted, never rewritten; new constraints that old data may violate are `NOT VALID`). Prove the migration by **running it twice** on a real Postgres engine (PGlite runner `scratchpad/pg/run-*.mjs` pattern, plus a `*.pg.test.ts` for CI). Check table/function names against `docs/*.sql` first (`CREATE TABLE IF NOT EXISTS` on an existing name silently does nothing). In Supabase every new table is born with ALL for `anon`/`authenticated`/`service_role`: `REVOKE ALL … FROM service_role` first, then grant. RLS by **workspace membership**, never a JWT claim. An internal SQL function is revoked from `PUBLIC, anon, authenticated`.
- **A migration is proven by running it, not reading it.** A test that only asserts SQL text is not evidence.
- **Never write "Post-migration Audit: PASS"** unless the human reported a real result. Write: `Post-migration verification query generated — PENDING HUMAN CONFIRMATION`.
