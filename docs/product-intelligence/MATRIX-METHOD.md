# Matrix Method, Definitions and Blind Spots

> Generated by `node scripts/audit/build-intelligence-reports.mjs`. Every number below is interpolated from
> `docs/audit/generated/master-matrix-summary.json` (produced by `scripts/audit/join-matrix.mjs`). Re-run
> `node scripts/audit/reconcile-counts.mjs` to prove the totals still add up.

## Pipeline

1. `node scripts/audit/build-route-inventory.mjs` — parses `backend/src`, resolves plugin
   prefixes from `backend/src/index.ts`, records method, path, file:line, guards,
   capabilities, services, tables/RPCs.
2. `node scripts/audit/build-hook-inventory.mjs` — parses `packages/api/src/hooks`, records
   method, URL, query key, invalidations.
3. `node scripts/audit/build-ui-inventory.mjs` — crawls the UI corpus and records which
   file imports which hook.
4. `node scripts/audit/join-matrix.mjs` — joins the three, classifies every route and every
   hook, writes the CSV and `master-matrix-summary.json`.
5. `node scripts/audit/build-intelligence-reports.mjs` — renders these pages from the JSON.
6. `node scripts/audit/reconcile-counts.mjs` — asserts every total and every report fact.

## Terms (used only with these meanings)

| Term                     | Definition                                                                                                                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **STATICALLY_CONNECTED** | A hook resolves to the route (URL match after parameter normalisation) **and** at least one non-test UI file imports that hook. An import/URL chain, not a runtime result.                |
| **RUNTIME_VERIFIED**     | The same chain, **plus** a test recorded in `docs/audit/generated/flow-evidence.json` executed the route's handler in this session and passed. Only routes listed there carry this label. |
| **HOOK_NO_UI_CONSUMER**  | The hook resolves to a registered route and **zero** UI files import it.                                                                                                                  |
| **HOOK_NO_ROUTE**        | The hook's URL matches no registered route and the hook is not a client utility.                                                                                                          |
| **ROUTE_NO_HOOK**        | The route has no hook at all.                                                                                                                                                             |
| **ORPHAN**               | Retired. Not used as a category anywhere in this audit.                                                                                                                                   |

## route_class

Computed by `join-matrix.mjs` from path prefix, guards and registries, in this order:

1. `INFRASTRUCTURE` — `platformAdminGuard`, admin/developer/migrations/cloud-migration/debug/
   system/oauth/cms/blog/ingest/events/updates/snapshots/marketplace/market prefixes, and
   any path segment matching webhook/cron/health/metrics/sitemap/jobs.
2. `PUBLIC_PAGE_API` — `/api/public/*`, the storefront prefix, blog/cms, and public
   auth/billing-plans/updates endpoints.
3. `PUBLIC_API` — the route is in `API_ROUTE_SCOPES` (a key opens it; no shop UI expected).
4. `UI_VIA_NON_HOOK` — a component, app-shell file, web page, desktop or mobile file calls the
   path directly with `apiClient`/`fetch`/`local-engine`.
5. `CUSTOMER_FACING_NO_UI` — an authenticated workspace route with none of the above. **This is
   the only class treated as a candidate gap.**

## Hook sub-classes for HOOK_NO_UI_CONSUMER

| Sub-class                          | How it is decided                                                                                  |
| ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| **CALLED_DYNAMICALLY_OR_INDIRECT** | Another source file calls the hook, or another non-barrel module in `packages/api/src` imports it. |
| **TEST_ONLY**                      | The name appears only in test files.                                                               |
| **DEAD_CANDIDATE**                 | No call, no import, no test. A candidate for review, not a deletion order.                         |

## Blind spots (read before trusting a count)

1. **No runtime.** Nothing here proves a route works. 85 `*.pg.test.ts` have never run on
   this machine (embedded Postgres fails with Windows error 1314). The strongest live word in
   this audit is `LIVE_UNVERIFIED`.
2. **String matching.** Hook↔route matching normalises parameters and a fixed singular/plural
   alias list. A hook that builds its URL from a variable the parser cannot see will show as
   `HOOK_NO_ROUTE` or `ROUTE_NO_HOOK`.
3. **Grep-based direct-call detection.** `UI_VIA_NON_HOOK` is decided by searching the corpus
   for the path with parameter placeholders. A path assembled at runtime is missed.
4. **6 duplicate hook names.** Consumer counts are per name, so the two definitions share
   one count. They are listed explicitly in `HOOK-INVENTORY.md`.
5. **Test association is textual.** A route is "tested" when a test file contains its path or a
   service symbol. That over-counts tests and never proves the test exercises the route.
6. **The matrix is a map, not a verdict.** A `CUSTOMER_FACING_NO_UI` route may be a deliberate
   backend-only endpoint; `UI-GAP-CLASSIFICATION.md` makes that call per route.
