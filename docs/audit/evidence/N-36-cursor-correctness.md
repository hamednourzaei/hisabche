# N-36 — is the pull cursor a commit-order cursor?

Date: 2026-10-26. Evidence kinds: **CODE** and **SQL** (static reading). **Not executed against a database**; the interleaving below is derived from documented PostgreSQL semantics (a `BIGSERIAL` value is taken from a sequence at INSERT time, outside transaction isolation, and becomes visible only when its transaction commits). Nothing was changed.

## Verdict

**`CONDITIONALLY_CONFIRMED` (P1).** The cursor is an _insertion id_, not a commit-order cursor. Nothing in the repository orders pull visibility by commit. A change can therefore be skipped permanently by a client that has already advanced past it. The condition is concurrency: two transactions writing synced rows in the same workspace (or any workspace — the sequence is global) overlap in time. It needs no malicious actor. Probability per overlap is small; the consequence (a device silently lacks a row until a full rehydrate) is silent data divergence.

## 2. Interleaving (the failure scenario)

| Step | Transaction A (e.g. invoice batch, ledger posting still running) | Transaction B (e.g. a payment)       | Device D                                 |
| ---- | ---------------------------------------------------------------- | ------------------------------------ | ---------------------------------------- |
| 1    | writes invoice row → trigger takes `sync_version = 100`          |                                      |                                          |
| 2    | still open                                                       | writes row → takes 101 → **commits** |                                          |
| 3    | still open                                                       |                                      | pulls: sees 101 only → stores cursor 101 |
| 4    | **commits** (log row 100 now visible)                            |                                      |                                          |
| 5    |                                                                  |                                      | pulls `> 101` → row 100 never returned   |

Result: D never learns of A's change until `mustRehydrate` (prune horizon passes 101) or a manual snapshot. Mitigating facts found: (a) the realtime/wake path (`sync-engine.ts:532-548`) only triggers a pull, it does not re-read earlier versions; (b) a later update of the same entity produces a new, larger log row, which repairs _that entity_ — a single missed row is self-healing only if the same entity is touched again; (c) the window is as long as the longest write transaction touching a synced table (invoice creation with ledger posting is the longest).

## 3. What would make it a REJECT

Any of: a read that bounds the page by the oldest in-flight transaction (`pg_snapshot_xmin`/`txid_snapshot`), a lock taken before `nextval` and held to commit, a client lookback window that re-asks `cursor − k`, or a change-log insert deferred to commit. None exists in the repository. The existing tests run against an in-memory fake with a monotonic counter and a single connection (`sync-invariants.test.ts`), so they cannot exhibit the interleaving; no Postgres test exercises two overlapping writers (and Postgres tests could not run here, GATE-04).

## 4. Classification and limits

- Class: `SYNC_ORDERING` — design defect, **CONDITIONALLY_CONFIRMED**, P1 (data divergence on devices, silent, not cross-tenant, not a security issue).
- Not established: how often overlapping transactions occur in production (`LIVE_UNVERIFIED`); whether Supabase's pooler serialises writes per workspace (not documented in the repository); whether the clients' periodic full reconciliation (if any) masks it — none was found.
- Minimum prerequisite for any fix (stated, not designed): the pull must only expose log rows whose transaction has committed _and_ all lower ids have resolved, or the client must re-read a bounded window below its cursor idempotently. Choosing between the two is an implementation decision outside this audit.
