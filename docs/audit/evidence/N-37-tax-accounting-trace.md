# N-37 — tax and discount through invoice → ledger → reports

Date: 2026-10-26. Evidence: **CODE** (file:line read) and **SQL** (static). Not executed against a database. Nothing was changed.

## Verdict

**Real defect, P1 (accounting integrity), with one P2 consistency defect. Not a reporting limitation and not an intentional simplification:** the codebase itself states that tax belongs to a liability account (`accountRoles` contains `tax`; the tax engine freezes a per-component breakdown "which is what a return is filed from"), yet no invoice posting ever touches that account.

## 2. Findings

| ID    | Finding                                                                                                                                                                                                                                                                                                                                                          | Class                                | Severity                          |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ | --------------------------------- |
| N-37a | A taxed sale credits the **full tax-inclusive total to sales**. Revenue and gross margin are overstated by the tax, the balance sheet shows no tax payable, and a purchase's input tax is capitalised into inventory/payable. The tax return (from `invoice_tax_lines`) and the ledger therefore cannot be reconciled to each other                              | real defect in posting               | **P1**                            |
| N-37b | **Two sources of tax per invoice.** `invoices.tax_total / total` (request rate, step 1) and `tax_minor / total_minor` (engine, step 2). The ledger uses the first, the return uses the second. When the workspace has configured tax rules the two can differ (per-item rates, inclusive pricing, compound, withholding, header discount not seen by the engine) | consistency defect                   | P2 (P1 when rules are configured) |
| N-37c | The engine's result is written **after** the response, unawaited. A failure leaves an invoice with ledger posting but no `invoice_tax_lines`: it is missing from the return, silently                                                                                                                                                                            | silent failure (CLAUDE §7.3 pattern) | P2                                |
| N-37d | Header discount is not part of the engine's input, so engine totals and header totals diverge for any invoice with a header discount                                                                                                                                                                                                                             | consistency                          | P2 (part of N-37b)                |

## 3. What is fine

- Discount/tax math is integer-minor, clamped, and bounded (no tax on an empty invoice).
- The receivable equals what the customer owes.
- The return keeps output and input separate and is not capped (`selectAllPages`).
- An unconfigured workspace (no tax rules) writes no tax rows — legitimate; for them N-37a only applies if they type a `taxRate`/`taxTotal` on the invoice, which then goes entirely to sales.

## 4. Why nothing caught it

`invoiceLedgerLines` tests assert balanced entries, which a single-total entry always is; no test posts a taxed invoice and compares the ledger with `getTaxReturn`. A balanced entry proves nothing about which accounts carry the tax.

## 5. Limits

The engine-vs-header divergence (N-37b) is derived from reading two code paths, not from running one invoice through both. The `tax` account's existence in a given workspace's chart was not checked (`ensureAccountsForRoles` creates roles on demand; it was not read for `tax`).

## 6. Decision needed from the owner (not designed here)

Whether the tax-inclusive total should split into sales + tax payable (and input tax into a recoverable account) — a product/accounting policy, affecting existing balances and the offline engine's twin posting.
