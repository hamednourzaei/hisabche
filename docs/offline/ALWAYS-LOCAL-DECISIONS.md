# Always-Local — decisions

Two kinds of entry:

- **Decided** — a question the F3F4 table did not answer, decided here and
  implemented, with the reason and the proof.
- **Closed** — a question that looked open and is not: the decision was taken,
  or the behaviour it described is already the behaviour that ships. Each one
  says which, with the evidence. Nothing in this file is waiting on a person.

| A1  | Does the offline edition also send `x-hisabche-queue: 1`?                                 | No. `localRequest` sets it only when the edition is not `offline` (D1/D2: the offline edition has no server to sync to, and its outbox must stay empty).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| A2  | Who stamps `x-hisabche-user-id`?                                                          | The shell's `registerLocalTransport` wrapper, from `currentOutboxOwner()` (F1) — the same source the device queue uses. The local engine falls back to `ctx.userId` when the header is absent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| A3  | Where does the post-push projection delete live?                                          | A local-engine route, `DELETE /invoices/:id/projection`, in one `db.transaction` over `invoice_item` + `invoice`. The engine owns those two tables (D3); the sync engine calls it after `resolveQueue(..., 'done')`. Not a new bridge method, so no IPC/schema plumbing and one owner for the tables.                                                                                                                                                                                                                                                                                                                                                                                                        |
| A4  | Where does the derived conflict state live?                                               | `packages/validation/src/schemas/conflict-state.ts` (`conflictState`), so the server and the screen read the same function (D5). No column, no second vocabulary. A resolution this build does not know reads `RESOLVED`, never `PENDING_REVIEW`.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| A5  | Where does the two-device test live?                                                      | `backend/src/__tests__/always-local-two-devices.test.ts`, domain-level (D11). `backend` does not depend on `@hisabche/local-engine`, so the test models the server's replay rule explicitly (commented) and uses the REAL M2 code for the conflict: `detectBreaches`, `breachKey`, `breachDivergences`.                                                                                                                                                                                                                                                                                                                                                                                                      |
| A6  | Does a resolved conflict need `resolved_by`?                                              | Only a HUMAN one. `ConflictService.record` auto-merges a non-financial field and files `status='resolved'`, `resolution='auto_merge'`, `resolved_at=now()`, **no** `resolved_by`. The trigger therefore exempts `auto_merge` from the decider rule and keeps `resolved_at` mandatory (proved in `sync-conflicts-forward.pg.test.ts`).                                                                                                                                                                                                                                                                                                                                                                        |
| A7  | What happens when a device resends a mutation that was already decided?                   | `record()` and `recordStockBreach()` return the decision that stands and write nothing. Without that guard the upsert would try `resolved → open`, the trigger would refuse, `fileConflict` would swallow the refusal, and the retry would look successful while changing nothing. Proved in `conflict-auto-merge.test.ts`.                                                                                                                                                                                                                                                                                                                                                                                  |
| A8  | Are the operational-pull trigger functions hardened?                                      | Yes: `SET search_path = public, pg_temp` and `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` added to `sync_bump_version` / `sync_record_change` (AGENTS §5). Behaviour unchanged; the pg test still proves the logging.                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| A9  | D10's «N sales awaiting confirmation» label                                               | **Implemented, not deferred.** The app-shell dashboard now reads the DEVICE when there is no network: `readDashboardSalesFromDevice` / `readDashboardKpisFromDevice` in `packages/api/src/hooks/dashboard.ts` call the local engine's `/analytics/sales` and `/analytics/dashboard` through `localRequest`, the range picker's window is applied to the device's rows, and `pendingInvoiceCount` travels to the chart card as `dashboard.pendingInvoices` in fa/af/en. A device that cannot answer falls through to the server, whose failure stays an error. `null` = unknown → no label; «0 waiting» is a different sentence. Proved in `packages/api/src/__tests__/dashboard-offline-read.test.ts` (5/5). |
| A10 | What does the operational window do with an invoice whose `date`/`status` cannot be read? | Keeps it. The filter is `date >= cutoff OR date IS NULL OR (status ≠ paid AND status ≠ cancelled) OR status IS NULL`. A sale dropped from the device is a sale the shop cannot see; the cost of one extra row is nothing next to a missing one.                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| A11 | Do the four operational entities carry `version` in the pull?                             | Yes. `sync-pull-columns.test.ts` requires `id, workspace_id, version` for every pulled entity, and the version is what a later edit sends back. Added to `warehouse`, `branch`, `exchange_rate`, `product_stock`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| A12 | Are the four operational entities recorded in the offline contract?                       | Yes: `offline-contract.test.ts` now says why each one syncs (read-only for a device, allow-list `[]`), and the old «exchange rate does not sync» entry was corrected — it does now, as reference data the device reads and never writes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

## Closed — the question looked open, and is not

| #   | Question                                                | Why it is closed                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| C1  | Making `InvoiceService.reverseEffects` public (D8 note) | There is no caller and there will not be one: D8 decides that **rejecting a conflict never reverses the sale** — the server already accepted it, and the rejection records the decision, the reason, who and when. Making the method public now would be a public door with nobody behind it, which the repository forbids (no dead code). The rule D8 protects is implemented and proved over real HTTP (`PENDING_REVIEW → REJECTED`, 39/39 in `http-integration-finance.test.ts`). |
| C2  | `client_request_id` on the invoice pull (D3 note)       | D3 says explicitly: if the column is not part of the pull, **do not add one**. The reconciliation it would have served is done instead by deleting the local projection after a successful push (`DELETE /invoices/:id/projection`, A3), so the next pull brings the server's row with the official number. There is nothing left to add.                                                                                                                                            |
| C3  | Employees in the operational pull                       | `employees` has **no `workspace_id`** (`docs/base-schema-migration.sql`): it is not scoped by the one security boundary, so a device pull of it cannot be tenant-safe. Pulling it would break AGENTS §1 to fill a gap that F2.3 never had — the operational set is warehouse, branch, exchange rate and stock. Recorded here as the reason, not as unfinished work.                                                                                                                  |
| C4  | Payments and the accounting tables on the device        | The local tables exist (`transaction`, `payment`, `payment_allocation`, `account`, `journal_entry`, `journal_line`) but are not pulled, on purpose: the ledger is the server's (D12, one financial engine), and the local dashboard derives money from `invoice.total`/`paid_amount`, which the local engine maintains. Replicating a double-entry ledger onto a device would create a second place where a balance is computed — the exact thing D12 forbids.                       |
