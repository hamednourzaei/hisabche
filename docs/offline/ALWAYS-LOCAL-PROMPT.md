# پرامپت: Always-Local + Server Sync (ویندوز و اندروید)

> این را کامل به ایجنت بده. هر بخش «بسنج» فقط خواندن و گزارش است؛ هر بخش «انجام بده» تغییر کد است. این دو را قاطی نکن.

---

## ⭐ دو اصل حاکم (بالاتر از هر بند دیگر)

**اصل ۱ — اول موجود، بعد هیچ چیز تازه.**
اگر معماری فعلی primitive لازم را دارد، آینده را پیاده نکن. دیتابیس محلی، outbox، موتور سینک، change log (`sync_change_log` / `sync_mutations` / cursor pull / `pg_notify`)، صف تعارض، توابع دامنه، شماره‌گذاری فاکتور و reconciliation را **دوباره استفاده کن**. فقط کوچک‌ترین مسیر موجودِ لازم را گسترش بده. هر abstraction تازه باید در گزارش با «چرا موجود کافی نبود» (فایل:خط) توجیه شود؛ بدون توجیه = رد.

**اصل ۲ — اولین نقطه‌ی پایان «Always-Local کامل» نیست.**
اولین milestone این است: ثابت کنی **یک صفحه‌ی موجود** در حالت **آنلاین** از API به Local DB سوییچ می‌کند، بدون ساختن موتور دامنه‌ی دوم. تا این ثابت نشده، فاز بعدی شروع نشود.

**مرکز کل کار:**

```
ONLINE  ≠ API READ
ONLINE  = Local DB READ + Background Sync
OFFLINE = Local DB READ + Queued Mutations
```

```
PostgreSQL  (FINAL AUTHORITY)
     ▲
     │  Sync / Reconcile
     ▼
Local SQLite  (operational mirror + local projections + outbox)
     ▲
     │  ALL UI READS
     ▼
Android / Windows app-shell
```

## ۱. قانون یک موتور مالی (Domain Core)

| لایه                                                                          | کجا اجرا می‌شود                                                             |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **محاسبه‌ی خالص** (FIFO/AVCO، COGS، سود، مانده‌ی طرف حساب، اثر سند دفتر، KPI) | **یک implementation** در هسته‌ی مشترک؛ سرور و دستگاه همان را import می‌کنند |
| ذخیره، مجوز، اعتبارسنجی نهایی، شماره‌ی رسمی                                   | **فقط سرور**                                                                |
| Local projection                                                              | فقط **نتیجه‌ی** همان هسته روی داده‌ی محلی؛ هیچ قاعده‌ی کسب‌وکار مستقل       |

- اگر تابعی که لازم داری به DB بسته است: هسته‌ی خالصش را **جدا کن و سرور را هم به همان وصل کن**. نسخه‌ی client-side کپی‌شده ممنوع است.
- گارد: تستی که نشان دهد هیچ فایل زیر app-shell/local-engine فرمول مالی خودش را ندارد (import از هسته‌ی مشترک، نه بازنویسی) — injection-test شود.

## ۲. فاز ۰ — بسنج (هیچ تغییر کدی)

فایل `docs/offline/ALWAYS-LOCAL-00-FINDING.md` با:

1. چرا مشتری آفلاین در فاکتورساز لود نمی‌شود؟ مسیر کامل کالا و مشتری کنار هم: کامپوننت → هوک → کش/SQLite، با فایل:خط. دقیقاً کجا دو مسیر جدا می‌شوند.
2. جدول: هر موجودیت (مشتری، کالا، موجودی به‌تفکیک انبار، فاکتور، خط، پرداخت، حساب/سند دفتر، کارمند، انبار، شعبه، ارز دفاتر، نرخ ارز) → جدول محلی دارد؟ چه کسی پرش می‌کند؟ UI از کجا می‌خواند (API / persisted-query-cache / SQLite)؟
3. **سینک موجود:** `sync_change_log` و cursor pull امروز کدام جدول‌ها را پوشش می‌دهند؟ حذف را چطور منتقل می‌کنند؟ کدام موجودیت‌های جدول بالا پوشش ندارند؟
4. کدام توابع مالی خالص‌اند و کدام به Supabase بسته‌اند.
5. **شماره‌گذاری فاکتور فعلی:** دقیقاً از کجا می‌آید (`nextval`؟ سری؟ شعبه؟ دوره‌ی مالی؟)، و شماره‌ی آفلاین امروز چطور ساخته می‌شود.
6. خروج از حساب امروز با outbox پر چه می‌کند.
7. حجم: برای workspace با ۱۰۰k فاکتور دیتابیس محلی چقدر می‌شود؛ با فرمول.

**تا این فایل نوشته نشده، هیچ تغییر کدی نه.**

## ۳. ترتیب اجرا (هر مرحله با اثبات خودش؛ مرحله‌ی بعد فقط بعد از اثبات قبلی)

```
F0 بسنج
 ↓ اثبات: مسیر فعلی کالا و مشتری مستند شد
F1 رفع مشتری آفلاین
 ↓ اثبات: یک صفحه‌ی موجود در حالت آنلاین از Local DB می‌خواند (milestone اصل ۲)
F2 Operational Dataset
 ↓ اثبات: آنلاین و آفلاین یک مسیر خواندن دارند
F3 تراکنش محلی فاکتور + projection
 ↓
F4 تعارض و reconciliation
 ↓
وریفای کامل
```

### F1 — انجام بده: رفع مشتری آفلاین

- مشتری را از **همان مسیری** بخوان که کالا می‌خواند. راه دوم نساز.
- تست آفلاین (شبکه قطع) + injection-test.
- سپس milestone اصل ۲: یک صفحه (پیشنهاد: فهرست مشتری‌ها) را در حالت آنلاین هم از Local DB بخوان؛ تست کن که صفحه برای همین داده درخواست شبکه‌ی مستقیم نمی‌زند.

### F2 — انجام بده: Local Operational Dataset

- **کل دیتابیس را دانلود نکن.** مجموعه‌ی عملیاتی: مشتری و کالای فعال، موجودی انبارهای مجاز کاربر، فاکتورهای باز + N روز اخیر (ثابت صریح، پیش‌فرض ۹۰)، مانده‌های باز، کارمندان فعال، ارز دفاتر و نرخ‌ها. داده‌ی بیرون از مجموعه ⇒ پیام صریح «آفلاین در دسترس نیست»، نه فهرست خالی.
- **مکانیزم سینک:** اگر `sync_change_log` فعلی می‌تواند این مجموعه را پوشش دهد، **همان** mechanism canonical است. cursor جدا به‌ازای جدول فقط وقتی مجاز است که فاز ۰ نشان داده باشد پوشش لازم وجود ندارد — با دلیل در گزارش.
- **Bootstrap مرحله‌ای:** ورود ⇒ داده‌ی ضروری ⇒ برنامه قابل استفاده ⇒ بقیه در پس‌زمینه. پیشرفت («آماده‌سازی اطلاعات: ۸۷٪»، «آخرین همگام‌سازی: ۲۰:۰۸ · ۳ تغییر در انتظار ارسال») روی **همان** نشانگر/سینک‌سنتر موجود.
- فیلتر همیشه `workspace_id`؛ عضو محدود به شعبه داده‌ی شعبه‌ی دیگر را pull نمی‌کند.
- عددی که رویش تصمیم گرفته می‌شود (موجودی هنگام فاکتور) از محلی خوانده می‌شود، ولی **سرور هنگام commit دوباره می‌سنجد**؛ کلاینت هرگز «من چک کردم» را دلیل نمی‌گیرد.
- endpoint تازه‌ی pull (فقط اگر لازم): `requireWorkspaceContext`، `selectAllPages`، بدون `.limit` روی خواندن مالی.

### F3 — انجام بده: تراکنش محلی و projection

- ثبت فاکتور آفلاین در **یک تراکنش SQLite**: فاکتور + خطوط + حرکت انبار + مانده‌ی طرف حساب + projection KPI + ردیف outbox. نیمه‌کاره ممنوع.
- همه‌ی محاسبه‌ها از هسته‌ی مشترک (§۱).
- **KPI محلی = داده‌ی سینک‌شده‌ی سرور + projection های در انتظار با برچسب صریح** («شامل ۲ فاکتور در انتظار تأیید»، کلید در سه زبان). قبل از reconciliation انتظار برابری با سرور نیست؛ **بعد از سینک کامل** باید برابر باشد.
- بهای نامعلوم `null`، نه `0`. بعد از commit، مقدار سرور جایگزین projection می‌شود.
- **شماره‌ی رسمی فقط از مکانیزم canonical شماره‌گذاری سرور** (همانی که فاز ۰ پیدا کرد؛ اگر `nextval` است، همان). سیستم شماره‌گذاری دوم نساز. آفلاین فقط شناسه‌ی موقت (مثلاً `OFF-<device>-<seq>`) با برچسب «موقت» در چاپ.
- کلید idempotency از id محلی سند، نه از تلاش ارسال.

### F4 — انجام بده: تعارض و تصمیم مالک

- وضعیت‌ها: `PENDING_REVIEW` → `ACCEPTED` | `REJECTED` | `RESOLVED`. گذار رو‌به‌جلو با trigger؛ «یک بار اجرا» = وضعیت در WHERE. اگر صف تعارض موجود وضعیت‌های خودش را دارد، همان را گسترش بده.
- **Reject حذف نیست.** باقی می‌ماند: سند، تصمیم، دلیل، تصمیم‌گیرنده، زمان، mutation اصلی. اگر روی سرور ثبت نشده بود، اثری ساخته نمی‌شود؛ اگر شده بود، از `reverseEffects` (`invoice.service.ts`). projection دستگاه برگردانده شود.
- **Accept** = commit با شماره‌ی رسمی؛ کمبود موجودی ⇒ همان قاعده‌ی M2.4.
- تصمیم فقط با مالک/نقش مجاز از `request.tenancy.role` در سرور. فروشنده وضعیت فاکتور خودش و دلیل را می‌بیند.
- همان صفحه‌ی تعارض موجود، گسترش‌یافته؛ route یا صفحه‌ی تازه نه.
- migration: additive، idempotent، `REVOKE ALL … FROM service_role` روی جدول/تابع تازه، rollback، VERIFY، pg test دوبار.

## ۴. خروج از حساب با تغییر سینک‌نشده

- **هرگز تغییر مالیِ سینک‌نشده را بی‌صدا نابود نکن.**
- outbox خالی ⇒ خروج عادی و پاک‌شدن داده‌ی محلی همان مالک (`user:workspace`).
- outbox پر و آنلاین ⇒ اول تلاش برای سینک، بعد خروج.
- outbox پر و آفلاین ⇒ خروج مخرب بسته است؛ دیالوگ صریح با تعداد تغییرهای در انتظار. داده‌ی محلی برای همان مالک نگه داشته می‌شود تا ورود دوباره و سینک. هیچ مسیری که داده را بدون تأیید صریح و بدون نگهداری امن outbox پاک کند.
- تغییر workspace: داده‌ی هر workspace جدا نگه داشته می‌شود؛ outbox یک workspace هرگز به دیگری فرستاده نمی‌شود.

## ۵. تست‌ها (رفتار را بسنج، نه implementation را؛ هرکدام injection-test)

1. آفلاین: فاکتورساز مشتری و کالا را نشان می‌دهد.
2. آنلاین هم صفحه‌های سوییچ‌شده از Local DB می‌خوانند (درخواست مستقیم برای همان داده صفر).
3. **دو دستگاه:** موجودی سرور ۵، هر دو آفلاین ۳ می‌فروشند ⇒ نتیجه **قطعی** است (هر بار همان) و همان قاعده‌ی M2.4 اعمال می‌شود؛ invariant: هیچ فاکتوری بی‌سابقه ناپدید نمی‌شود، و موجودی/دفتر سرور با قاعده‌ی M2.4 سازگار است (مانده‌ها را بسنج، نه تعداد ردیف). وضعیت خاصی مثل `PENDING_REVIEW` را hardcode نکن مگر همان چیزی باشد که M2.4 تعریف کرده.
4. reject ⇒ سند، دلیل، تصمیم‌گیرنده و mutation اصلی باقی است.
5. KPI: قبل از سینک = سرور + pending برچسب‌دار؛ بعد از سینک کامل = KPI سرور (fixture دو ارز).
6. شناسه‌ی موقت هرگز شماره‌ی رسمی سرور نمی‌شود؛ شماره‌ی رسمی از مکانیزم canonical.
7. ارسال دوباره‌ی همان outbox ⇒ یک فاکتور.
8. خروج با outbox پر و آفلاین ⇒ هیچ mutation از دست نمی‌رود.
9. عضو محدود به شعبه داده‌ی شعبه‌ی دیگر را pull نمی‌کند.
10. گارد یک موتور مالی (§۱).

## ۶. پایان کار

ترتیب: وریفای کامل (tsc همه‌ی پکیج‌ها، backend vitest، ui vitest، desktop jest، mobile jest) → eslint روی فایل‌های تغییرکرده از پوشه‌ی همان پکیج → بیلد ویندوز (`electron-builder --win --publish never -c.electronDist=node_modules/electron/dist`، probe `better_sqlite3` با `ELECTRON_RUN_AS_NODE=1`) و اندروید (`pnpm --filter @hisabche/mobile android:release`، **تاریخ APK** را چک کن) → درس‌ها → `graphify.exe . --update`.

گزارش فارسی شامل: هر abstraction تازه با توجیه «چرا موجود کافی نبود»، جدول عددهای واقعی، و یکی از وضعیت‌ها: `VERIFIED_COMPLETE` · `IMPLEMENTED_NOT_LIVE_VERIFIED` · `BLOCKED_EXTERNAL_CREDENTIAL` · `BLOCKED_BY_EXISTING_SYSTEM` · `NOT_APPLICABLE` · `FAILED`. بدون HTTP یا دیتابیس واقعی هیچ چیز `VERIFIED_COMPLETE` نیست. ادعای PASS بدون خروجی فرمان ممنوع.

**اگر وسط کار دیدی کار از یک مرحله بزرگ‌تر شد، همان‌جا بایست، گزارش مرحله‌ی تمام‌شده را بده و ادامه نده.**
