## 3. Deviations — every one, with its file

The bootstrap was not a straight line. Each deviation below is a fact about the
repository's own queue, not about the lab.

### 3.1 Skipped files — 55 (51 driver + 4 manual)

Classes: **48 `VERIFY-*`** · **5 `FINDING-*`** · `DUMP-STRUCTURE-ONLY.sql` ·
`WIPE-ALL-BUSINESS-DATA.sql`.

- **The structural reason.** The runner's extras order is alphabetical, and
  uppercase sorts before lowercase: every `VERIFY-*` file runs **before** the
  `*-migration.sql` whose objects it verifies. On a fresh database they fail
  with `relation … does not exist`. That is what 48 of the skips are.
- **The driver's skip rule (51 files)** — a file is recorded SKIPPED only after
  stripping comments, string literals and dollar-quoted bodies and finding no
  `CREATE/ALTER/DROP/GRANT/REVOKE/TRUNCATE/INSERT/UPDATE/DELETE/COPY/EXECUTE/CALL/VACUUM/REINDEX/CLUSTER/INTO`
  and no `DO` block: it provably cannot change the schema. A skip can never
  change what the rebuild produces.
- **Marked by hand (4):** `DUMP-STRUCTURE-ONLY.sql` (its section-3 query also
  has a **real bug**: it references `pg_stat_user_tables` as if it had an
  `oid` column — §4.2), `FINDING-1-SUSPENDED-MEMBERS.sql` and
  `FINDING-7-WHY-NO-COSTING.sql` (query objects created by later-sorted files;
  FINDING-7's third query additionally has a GROUP BY that omits a selected
  column — §4.3), `WIPE-ALL-BUSINESS-DATA.sql` (RAISEs by design; an operator
  file that needs a human edit before it does anything).
- Every skip carries the triggering error and the reason in
  `schema_migrations.applied_by`; a dump is in
  `raw/M1-db-skips-from-schema-migrations.json`.

### 3.3 Ordering repair — one, recorded in `raw/M1-ordering-repairs.json`

`phase-c-01` line 128 (`ALTER TABLE products ALTER COLUMN quantity TYPE
numeric(18,4)`) was blocked by `cannot alter type of a column used in a trigger
definition`. The trigger is `products_stock_webhook_trg`, created by
`developer-platform-02-migration.sql` (lines 214–219, `AFTER UPDATE OF quantity,
min_stock_level … WHEN old/new differ`). Alphabetically `developer-platform-*`
(d) runs before `phase-*` (p) — but on the live database the chronology was the
opposite, so the conflict never existed there. Repair, exactly:

1. `DROP TRIGGER IF EXISTS products_stock_webhook_trg ON public.products` — the
   statement from line 214 of its own file, after verifying no view depends on
   `products.quantity` (pg_depend probe → none) and that this was the only such
   conflict (8 column-pinning triggers × the only 2 `ALTER COLUMN TYPE`
   statements in `docs/`).
2. After the queue completed, `developer-platform-02-migration.sql` was re-run
   from its own bytes (`sql-file`, 28 statements) — it contains no
   `INSERT`/`COPY`, only idempotent DDL and grants — and the trigger is back:
   `CREATE TRIGGER products_stock_webhook_trg AFTER UPDATE OF quantity,
min_stock_level ON public.products …` (confirmed present).

### 3.5 Tooling defect found and fixed — platform-binary resolution

The lab initially resolved `@embedded-postgres/windows-x64` to a **stray global
install one level above the repo** (`C:\Users\hamed\node_modules\…`, version
18.4), which cannot open a v17 cluster — symptom: `database files are
incompatible with server`. Fixed by resolving the platform package from the
`embedded-postgres` library itself (as its own `binary.js` does) plus a
pre-spawn guard that refuses any binary whose major version differs from the
data directory's `PG_VERSION`. Also: the embedded distribution ships no
`pg_controldata`, so `pg_ctl` is unusable here and the lab starts `postgres.exe`
directly (see `TOOLING.md` traps 1–2).

## 8. Addendum (same day) — the first defect the rebuild exposed, fixed and proven

### 8.1 The defect

On the fresh rebuild — and **only** on a fresh rebuild — a workspace owner was
born «suspended», every invoice was born «finalized», every account and every
posted journal entry was born «deleted», every password-reset token was born
«used and revoked», and every new user skipped onboarding. Root cause:
`docs/base-schema-migration.sql` declares `DEFAULT now()` on 29 nullable
timestamps whose meaning is «has not happened yet», inside
`CREATE TABLE IF NOT EXISTS` blocks that never applied on the live database
(the tables already existed there). The live product therefore never had these
defaults; a rebuilt database got every one of them.

### 8.2 The fix

`docs/semantic-null-defaults-migration.sql` — 29 columns across 22 tables, one
transaction, `SET LOCAL lock_timeout = '5s'`, full Rollback block; plus the
read-only `docs/VERIFY-semantic-null-defaults.sql` (29 column checks + the
whole-class invariant «no nullable timestamp defaults to now()» + a
no-overreach check), plus
`backend/src/__tests__/semantic-null-defaults.pg.test.ts` (builds the defect
itself, runs the migration **twice**). Two evidence classes, neither a guess:

- **10 columns** — a reader in the repository treats NULL as «not yet» and the
  writer omits the column (file:line citations in the migration header;
  precedent: the owner's own `docs/multi-warehouse-migration.sql:50`);
- **19 more** — the production schema itself carries no default on them.

### 8.5 The 136 remaining differences — classified, not fixed

- **63 = `created_at` / `updated_at`** (38 + 25). Production is mid-migration:
  `docs/module-created-at-default-migration.sql` moves live **toward** having
  these defaults; the rebuild already carries the destination state. Not a
  defect — it is the owner's own direction.
- **73 = nullable booleans / numerics / jsonb** (`products.is_active`
  DEFAULT true, `invoices.subtotal` DEFAULT 0, `customers.opening_balance`
  DEFAULT 0, …). Source: `scripts/generate-base-schema.mjs` deliberately infers
  these defaults (its header documents the day-long outage that made inference
  necessary). `docs/restore-defaults-migration.sql` is scoped to NOT NULL
  columns only, so live never got them on nullable ones. **Direction: keep in
  the rebuild** — the application behaves as if they are present, and every row
  this lab seeds is written explicitly, so the difference exists only for
  inserts that omit the column. The full list sits in
  `raw/M2-prod-vs-lab-defaults.json` for the parity chapter of the final report.

### 8.6 Open finding — the password-reset insert vs the workspace FK

`password-reset.service.ts:93-100` inserts
`workspace_id = '00000000-0000-0000-0000-000000000000'`. On the rebuilt
database this is **refused**: `password_reset_tokens_workspace_id_fkey` is
`NOT VALID` — which skips old rows but still enforces new inserts — and no
zero-uuid target exists (measured: the probe's first run failed with exactly
that foreign-key violation). Production's dump carries the same FK, so unless a
zero-uuid `workspaces` row exists there, token creation fails live as well —
the service logs `Error saving reset token` and answers «Failed to process
request». One query decides it, for the owner:

```sql
SELECT id, name FROM workspaces WHERE id = '00000000-0000-0000-0000-000000000000';
```

If it returns nothing, the fix direction is to write the member's real
workspace (the service already fetches it at line 87) or NULL. Not changed
here — the decision is the owner's.
